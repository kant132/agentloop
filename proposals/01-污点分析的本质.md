# 污点分析的本质：一个认识论问题

> 本文不是规则清单。本文试图回答一个根本问题：**为什么大模型做不好污点分析？**
> 答案不在于模型不够聪明，而在于模型对「污染」这个概念的理解是**语法层面**的，而非**语义层面**的。

---

## 一、污点分析不是「找路径」，而是「理解变换」

### 1.1 表象：从 source 到 sink 的数据流

所有教科书、所有工具、所有 LLM 都把污点分析简化为一个图论问题：

`
source（外部输入）→ 中间节点 → sink（危险函数）
`

然后判断：路径上有没有消毒器？有 = 安全，无 = 漏洞。

**这是错的。** 或者说，这是极度肤浅的。

### 1.2 本质：数据在每一层经历了什么语义变换？

真正的污点分析问的不是「数据有没有被消毒」，而是：

> **数据在每一层被如何变换？变换后的数据在当前上下文中是否仍然危险？**

举个例子：

`java
// 场景 A：看起来安全，实际危险
String name = request.getParameter("name");     // source: 未信任
String safe = name.trim();                      // 变换：去空白（语义无关）
String sql = "SELECT * FROM users WHERE name='" + safe + "'";  // 拼接：仍然危险
PreparedStatement ps = conn.prepareStatement(sql);  // 看起来消毒了？
// 实际：prepareStatement 接收的已经是拼接好的 SQL，setXxx 根本没用到
`

`java
// 场景 B：看起来危险，实际安全
String name = request.getParameter("name");     // source: 未信任
int id = Integer.parseInt(name);                // 变换：强类型转换（语义消毒）
String sql = "SELECT * FROM users WHERE id=" + id;  // 拼接：但 id 已经是 int
`

LLM 看到场景 A 会说「有 PreparedStatement，安全」——因为它在做**模式匹配**，不是语义分析。
LLM 看到场景 B 会说「有拼接，危险」——同样在做模式匹配。

**两个都判断错了。**

### 1.3 污点分析的三层认知

| 认知层次 | 描述 | LLM 能力 |
|---------|------|---------|
| **L1 路径存在性** | source → sink 有没有路径？ | ✅ 能做（codegraph 辅助） |
| **L2 消毒器识别** | 路径上有没有消毒函数？ | ⚠️ 部分能做（模式匹配） |
| **L3 语义变换理解** | 消毒器是否真正改变了数据的语义？ | ❌ 几乎不能做 |

**当前实现停留在 L2。** conduct/必读/07-剪枝逻辑硬约束.md 的消毒器清单本质上还是模式匹配：看到 PreparedStatement + setXxx 就认为消毒了。但没有验证 setXxx 是否真的被用到了。

## 二、消毒器的语义分类

消毒器不是同质的。不同类型的消毒器对不同类型的 sink 有效。LLM 经常混淆这一点。

### 2.1 类型转换型消毒

**本质**：把数据从一个语义域映射到另一个语义域，使得目标域不可能包含攻击 payload。

| 消毒器 | 源域 | 目标域 | 有效 sink |
|--------|------|--------|----------|
| Integer.parseInt | String | int | SQLi, XSS, RCE（全部） |
| Enum.valueOf | String | enum | 全部 |
| Boolean.parseBoolean | String | boolean | 全部 |

**关键**：类型转换型消毒是**绝对消毒**。一旦数据变成 int，它就不可能包含 SQL 注入 payload。LLM 经常不把这个当作消毒，继续追踪，浪费 token。

### 2.2 编码型消毒

**本质**：把数据从一种编码形式转换为另一种，使得目标编码形式中特殊字符失去语义。

| 消毒器 | 编码 | 有效上下文 | 无效上下文 |
|--------|------|-----------|-----------|
| HtmlUtils.htmlEscape | HTML 实体 | HTML body 中的 XSS | SQL（无效） |
| URLEncoder.encode | URL 编码 | URL 参数中的 XSS | SQL（无效）、HTML body（部分无效） |
| StringEscapeUtils.escapeSql | SQL 转义 | SQL | HTML（无效） |

**关键**：编码型消毒是**上下文相关的**。HTML 转义对 SQL 无效，URL 转义对 HTML body 中的 XSS 部分无效（如 <script> 标签内的 URL 编码字符串会被浏览器解码后执行）。

LLM 最常犯的错误：看到 HtmlUtils.htmlEscape 就认为所有注入都被消毒了，不管 sink 类型。

### 2.3 参数化型消毒

**本质**：把数据和指令分离，使得数据永远不被解释为指令。

| 消毒器 | 分离方式 | 有效 sink |
|--------|---------|----------|
| PreparedStatement + setXxx | SQL 参数绑定 | SQLi |
| MyBatis #{} | 参数占位符 | SQLi |
| ProcessBuilder 参数列表 | 参数数组（非 shell 拼接） | RCE |

**关键**：参数化型消毒要求**数据和指令从未混合**。如果在 prepareStatement 之前已经拼接了用户输入，那 setXxx 就是无效的。

LLM 最常犯的错误：看到 prepareStatement 就认为安全，不检查 SQL 是否在 prepareStatement 之前已经被拼接。

### 2.4 校验型消毒

**本质**：检查数据是否符合预期格式，不符合则拒绝。

| 消毒器 | 校验方式 | 强度 |
|--------|---------|------|
| 正则白名单 Pattern.matches("[a-z]+") | 只允许特定字符 | 强 |
| 正则黑名单 Pattern.matches(".*['\";].*") | 拒绝特定字符 | 弱（易绕过） |
| 长度限制 str.length() <= 10 | 限制长度 | 中 |
| 枚举校验 ALLOWED.contains(val) | 白名单集合 | 强 |

**关键**：校验型消毒的强度取决于校验的严格程度。白名单强，黑名单弱。LLM 经常不区分黑白名单，看到 Pattern.matches 就认为消毒了。

## 三、LLM 在污点分析中的七个认知缺陷

### 缺陷 1：混淆消毒器的存在性和有效性

**表现**：看到 PreparedStatement 就认为 SQL 已消毒，不检查是否真的用了 setXxx。

**根因**：LLM 的模式匹配是二元的——要么看到消毒器，要么没看到。它不理解消毒器的有效性需要满足多个条件。

**修复**：消毒器有效性检查必须包含：
1. 消毒器是否存在？
2. 消毒器是否被正确调用？（setXxx 是否被调用）
3. 消毒器是否在拼接之前调用？（时序正确性）
4. 消毒器是否对当前 sink 类型有效？（上下文相关性）

### 缺陷 2：不理解跨方法的污点传播

**表现**：方法 A 调用方法 B，方法 B 调用方法 C。LLM 只看 A→B，不看 B→C 中参数是否被变换。

**根因**：LLM 的注意力窗口有限，追踪深度一深就丢失上下文。

**修复**：每一层方法调用必须明确记录：
- 输入参数的语义状态（trusted/untrusted/partially_sanitized）
- 方法内部对参数的变换
- 输出参数的语义状态

### 缺陷 3：不理解反射和动态分派的污点传播

**表现**：Method.invoke(obj, args) 中 args 的污点状态丢失。proxy.invoke(args) 中不知道 proxy 实际调用什么。

**根因**：LLM 无法在静态分析中解析动态分派。

**修复**：遇到反射/代理，标注 
eeds_dynamic_analysis，降级为「可能传播」。

### 缺陷 4：不理解集合和容器的污点传播

**表现**：List<String> 中某个元素被污染，LLM 认为整个 List 都污染或都不污染。

**根因**：LLM 不理解集合内部的元素级污点传播。

**修复**：
- list.add(untrusted) → 该索引位置污染
- list.get(i) → 如果 i 可控，返回污染值
- map.put(key, untrusted) → 该 key 对应的 value 污染
- map.get(key) → 如果 key 匹配，返回污染值

### 缺陷 5：不理解异常处理的污点传播

**表现**：catch (Exception e) 中 e.getMessage() 可能包含用户输入，但 LLM 不追踪。

**根因**：LLM 不认为异常消息是污点传播路径。

**修复**：
- 	hrow new MyException(userInput) → 异常消息污染
- catch 块中 e.getMessage() → 可能污染
- 异常消息写入日志 → 信息泄露

### 缺陷 6：不理解回调和异步的污点传播

**表现**：CompletableFuture.thenApply(x -> process(x)) 中 x 的污点状态丢失。

**根因**：LLM 不理解异步回调的参数传递。

**修复**：
- 	henApply / 	henAccept / 	henCompose 的参数继承上游的污点状态
- @Async 方法的参数继承调用方的污点状态
- MQ 消费者的消息体继承生产者的污点状态

### 缺陷 7：不理解框架隐式消毒

**表现**：Spring MVC 的 @RequestParam 自动做了 URL 解码，但 LLM 不知道。Thymeleaf 默认转义 HTML，但 LLM 不知道。

**根因**：LLM 的训练数据不包含所有框架的隐式行为。

**修复**：
- 项目使用什么框架 → 加载该框架的隐式消毒清单
- 存到 projects/{groupId}/implicit-sanitizers.json
- FWD-A 启动时加载

## 四、当前实现的批判

### 4.1 消毒器清单的问题

conduct/必读/07-剪枝逻辑硬约束.md 的消毒器清单（3.2 节）是一个好的开始，但它有两个根本问题：

1. **它是二元的**：要么有效，要么无效。没有「部分有效」「上下文有效」的概念。
2. **它是静态的**：清单写死了，不会根据项目特征动态调整。

**改进**：消毒器清单应该是一个**决策矩阵**，行是消毒器，列是 sink 类型，值是「有效/无效/部分有效/需验证」。

### 4.2 剪枝逻辑的问题

L2 链级剪枝的判定流程（3.1 节）过于简化：

`
是否调用了消毒器？→ 检查 sanitizer 清单 → 已被有效消毒 → PRUNE
`

这个流程没有考虑：
- 消毒器的时序正确性
- 消毒器的上下文相关性
- 消毒器的完整性（是否覆盖了所有参数）

### 4.3 FWD-A 的问题

java-forward-vuln-discovery/SKILL.md 的 FWD-A 模式说「每节点过 D1（危险 sink）+ sanitizer 检测」，但没有定义 D1 的判定逻辑。什么算「危险 sink」？只有清单上的函数？还是任何可能有副作用的函数？

## 五、改进提议

### 提议 1：引入「语义变换记录」

每个链节点必须记录数据的语义变换：

`json
{
  "fqn": "com.example.UserService.findByName",
  "input_params": [
    {"name": "name", "type": "String", "taint": "untrusted", "semantic": "user_input"}
  ],
  "transforms": [
    {"operation": "trim", "semantic_change": "none", "taint_after": "untrusted"},
    {"operation": "Integer.parseInt", "semantic_change": "string_to_int", "taint_after": "trusted"}
  ],
  "output_params": [
    {"name": "id", "type": "int", "taint": "trusted", "semantic": "parsed_integer"}
  ]
}
`

### 提议 2：消毒器有效性矩阵

创建 types/消毒器矩阵.md，明确每种消毒器对每种 sink 的有效性：

| 消毒器 | SQLi | XSS(html) | XSS(js) | XSS(url) | RCE | 路径遍历 | SSRF | 反序列化 |
|--------|------|-----------|---------|----------|-----|---------|------|---------|
| PreparedStatement+setXxx | ✅ | ❌ | ❌ | ❌ | ❌ | ❌ | ❌ | ❌ |
| HtmlUtils.htmlEscape | ❌ | ✅ | ❌ | ❌ | ❌ | ❌ | ❌ | ❌ |
| URLEncoder.encode | ❌ | ❌ | ⚠️ | ✅ | ❌ | ✅ | ⚠️ | ❌ |
| Integer.parseInt | ✅ | ✅ | ✅ | ✅ | ✅ | ✅ | ✅ | ✅ |
| Pattern.matches(白名单) | ✅ | ✅ | ✅ | ✅ | ✅ | ✅ | ✅ | ✅ |
| Pattern.matches(黑名单) | ⚠️ | ⚠️ | ⚠️ | ⚠️ | ⚠️ | ⚠️ | ⚠️ | ⚠️ |

### 提议 3：引入「污点衰减」概念

污点不是二元的（trusted/untrusted），而是一个连续值：

- untrusted：直接来自外部输入，未经任何处理
- weakly_sanitized：经过了弱消毒（如黑名单过滤）
- strongly_sanitized：经过了强消毒（如白名单校验）
- 	rusted：经过了类型转换或参数化

FWD-A 的判定应该基于污点程度和 sink 危险等级的匹配：
- untrusted → 任何 sink 都报漏洞
- weakly_sanitized → 高危 sink 报漏洞，低危 sink 报提示
- strongly_sanitized → 高危 sink 报提示，低危 sink 不报
- 	rusted → 不报

---

## 六、一句话总结

**污点分析的本质不是找路径，而是理解数据在每一层经历了什么语义变换。LLM 做不好这件事，因为它只会模式匹配，不会语义推理。修复方向不是写更多规则，而是教会 LLM 如何记录和分析语义变换。**
