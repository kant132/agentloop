# 马斯克：第一性原理分析

> 方法：把所有假设剥掉，从物理学层面思考「这件事的本质是什么」，然后找最短路径。

---

## 第一步：定义本质问题

**问题**：Java 代码白盒安全审计的本质是什么？

**物理学层面的回答**：

代码是一堆文本。漏洞是文本中的一种模式——外部输入（source）通过一系列变换（transforms），到达危险操作（sink），且变换过程中没有有效的消毒（sanitizer）。

所以审计的本质是一个**模式匹配问题**：

`
输入：源代码文本 + 业务规则
输出：所有 (source, transforms, sink, sanitizers) 四元组，其中 sanitizers 不足以阻断 source → sink 的传播
`

这就是全部。没有 Phase、没有 Skill、没有评分。这些是**实现细节**，不是本质。

## 第三步：为什么当前实现这么慢？

### 3.1 Phase 1-3 是预计算，可以用工具替代

**Phase 1（文档+环境）**：
- 读文档 → 可以用脚本提取关键信息
- 识别环境 → 可以用脚本检测
- 反编译 JAR → 可以用 jadx 自动化

**Phase 2（威胁建模）**：
- STRIDE 分析 → 可以从 source/sink 类型自动推断
- 攻击树 → 可以从调用链自动生成
- 数据流图 → 可以从 codegraph 自动导出

**Phase 3（Filter 分析）**：
- Filter 链分析 → 可以用 codegraph SQL 自动提取
- 消毒器识别 → 可以用 ast-grep 自动标注

**结论**：Phase 1-3 的 80% 工作可以用工具自动化，不需要 LLM。

### 3.2 Phase 4 是枚举，可以用 codegraph 一次完成

**当前做法**：LLM 读代码，找端点。

**更优做法**：codegraph SQL 一次查询所有端点。

`sql
SELECT m.fqn, m.signature, a.name as annotation
FROM methods m
JOIN annotations a ON m.id = a.method_id
WHERE a.name IN ('@GetMapping', '@PostMapping', '@RequestMapping', '@DubboService', '@WebServlet')
`

**结论**：Phase 4 可以用一条 SQL 替代，不需要 LLM。

### 3.3 Phase 5 是唯一需要 LLM 的阶段

**当前做法**：4 种 FWD 模式，每种模式启动一个 subagent。

**更优做法**：
- 用 codegraph + ast-grep 预计算所有 source → sink 路径
- 标注每条路径上的消毒器
- 把路径分批（每批 10 条）扔给 LLM，让 LLM 判断安全性

**结论**：Phase 5 可以简化为「LLM 判断路径安全性」，不需要 4 种模式。

## 第四步：最优解是什么？

### 4.1 工具层（自动化，0 Token）

`
工具 1：source-sink-extractor
  - 输入：项目源代码
  - 输出：所有 (source, sink) 对
  - 实现：codegraph SQL + ast-grep

工具 2：chain-extractor
  - 输入：(source, sink) 对
  - 输出：所有 source → sink 的调用链
  - 实现：codegraph CTE RECURSIVE

工具 3：sanitizer-annotator
  - 输入：调用链
  - 输出：标注了消毒器的调用链
  - 实现：ast-grep 模式匹配
`

### 4.2 LLM 层（判断，300K Token）

`
任务 1：判断路径安全性
  - 输入：标注了消毒器的调用链（10 条/批）
  - 输出：每条路径的安全性判断 + 理由
  - 约束：考虑消毒器的时序、上下文、完整性

任务 2：生成报告
  - 输入：所有安全性判断
  - 输出：人类可读的报告
`

### 4.3 反馈层（持久化，跨轮次）

`
存储 1：项目知识
  - 业务规则、自定义注解、框架特性
  - 存到 Memurai，跨轮次复用

存储 2：审计经验
  - 假阳、假阴、优化建议
  - 存到 Memurai，跨项目复用
`

## 第五步：从当前实现到最优解的路径

### 5.1 第一阶段：简化工具层（1 周）

**目标**：把 Phase 1-4 的 80% 工作自动化。

**行动**：
1. 写 source-sink-extractor.py：用 codegraph SQL 提取所有 source/sink
2. 写 chain-extractor.py：用 codegraph CTE 提取所有调用链
3. 写 sanitizer-annotator.py：用 ast-grep 标注消毒器
4. 主 SKILL.md 压缩到 50 行，只描述 LLM 的任务

**预期效果**：Phase 1-4 从 2.75h 减少到 30min。

### 5.2 第二阶段：简化 LLM 层（1 周）

**目标**：把 Phase 5 从 4 种模式简化为 1 个任务。

**行动**：
1. 删除 4 种 FWD 模式的区分（A/B/C/D）
2. LLM 只做一个任务：判断路径安全性
3. 每条路径的判断独立，不依赖其他路径

**预期效果**：Phase 5 从 4h 减少到 2h。

### 5.3 第三阶段：建立反馈层（1 周）

**目标**：建立持久化机制，让每轮审计都比上一轮更好。

**行动**：
1. 用 Memurai 存储项目知识（业务规则、自定义注解）
2. 用 Memurai 存储审计经验（假阳、假阴、优化建议）
3. 每轮结束时同步到文件，跨轮次复用

**预期效果**：第 2 轮审计比第 1 轮快 30%。

## 马斯克式结论

**核心问题**：当前实现偏离了第一性原理。

**偏离度**：
- 时间：2.3x（7h vs 3h）
- Token：2.3x（800K vs 350K）
- 复杂度：高（6 阶段 vs 4 步骤）

**根本原因**：把可以用工具自动化的工作交给了 LLM。

**修复方向**：
1. 工具层：自动化 Phase 1-4 的 80% 工作
2. LLM 层：简化 Phase 5，只做「判断路径安全性」
3. 反馈层：建立持久化机制，跨轮次复用

**一句话**：最好的 Phase 是不存在的 Phase。能用工具做的，不要用 LLM。
