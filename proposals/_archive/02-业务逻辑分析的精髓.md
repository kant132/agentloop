# 业务逻辑分析的精髓：一个本体论问题

> 本文试图回答：**业务逻辑漏洞和注入类漏洞有什么根本区别？为什么这个区别决定了 LLM 几乎不可能独立发现业务逻辑漏洞？**

---

## 一、业务逻辑漏洞没有 sink

### 1.1 注入类漏洞的结构

所有注入类漏洞共享同一个结构：

`
外部输入 → [污点传播] → 危险函数（sink）
`

sink 是**预定义的、已知的、可枚举的**。Runtime.exec、JdbcTemplate.query、ObjectInputStream.readObject —— 这些函数在安全社区已经被编目了几十年。审计者只需要找到从 source 到 sink 的路径，然后判断路径上有没有消毒器。

这是一个**搜索问题**。LLM 可以做搜索。

### 1.2 业务逻辑漏洞的结构

业务逻辑漏洞的结构完全不同：

`
外部输入 → [业务处理] → 业务结果
                ↑
        这里没有 sink
`

**没有预定义的危险函数。** 代码本身可能是完全正确的——没有 SQL 注入、没有 XSS、没有 RCE。但它做的事情**违反了业务规则**。

举例：

`java
// 这段代码没有任何注入漏洞
// 但它有一个严重的业务逻辑漏洞
@PostMapping("/order/pay")
public Result pay(@RequestBody PayRequest req) {
    Order order = orderService.getById(req.getOrderId());
    // 没有校验 order.getUserId() == currentUser.getId()
    // 攻击者可以替别人的订单付款（或者更糟：替别人的订单确认收货）
    paymentService.pay(order.getId(), req.getAmount());
    orderService.updateStatus(order.getId(), "PAID");
    return Result.success();
}
`

这段代码的「漏洞」在哪里？不在任何一个函数调用里。它在于**缺少一个校验**：order.getUserId() == currentUser.getId()。

**这个校验不存在于代码中。它只存在于业务规则中。**

### 1.3 这意味着什么？

这意味着：

1. **你不能通过扫描代码来发现业务逻辑漏洞**——因为代码本身没有「错误」
2. **你必须先理解业务应该怎么做**——然后才能发现代码偏离了什么
3. **「应该怎么做」不在代码里**——它在文档里、在开发者的脑子里、在行业惯例里

**这就是为什么业务逻辑漏洞是 LLM 最难发现的。** 不是因为 LLM 不够聪明，而是因为发现这类漏洞需要的信息**不在代码里**。

## 二、业务逻辑漏洞的四种本体论类型

### 2.1 缺失校验型

**本质**：代码没有验证某个业务前提条件。

| 子类型 | 缺失的校验 | 攻击 |
|--------|-----------|------|
| **归属校验** | 对象是否属于当前用户 | IDOR（替别人操作） |
| **状态校验** | 前置状态是否满足 | 跳过流程步骤 |
| **权限校验** | 当前用户是否有权 | 越权操作 |
| **数量校验** | 数量是否在合理范围 | 超卖、负数购买 |
| **频率校验** | 操作频率是否合理 | 刷单、薅羊毛 |

**LLM 缺陷**：LLM 不知道「这个对象应该属于当前用户」——这是业务规则，不是代码规则。除非文档明确写了「用户只能操作自己的订单」，否则 LLM 无法推断。

### 2.2 逻辑矛盾型

**本质**：代码实现了两个互相矛盾的业务规则。

| 子类型 | 矛盾 | 攻击 |
|--------|------|------|
| **价格矛盾** | 前端传价格 + 后端算总价 | 篡改单价 |
| **数量矛盾** | 不校验库存 + 允许下单 | 超卖 |
| **状态矛盾** | 允许退款 + 允许同时发货 | 双重获利 |

**LLM 缺陷**：LLM 不会主动寻找矛盾。它看到「前端传价格」不会想到「后端也应该校验价格」，因为这需要理解价格的业务含义。

### 2.3 时序依赖型

**本质**：代码假设操作按特定时序发生，但没有强制保证。

| 子类型 | 时序假设 | 攻击 |
|--------|---------|------|
| **并发问题** | 扣款和发货是原子的 | 并发下单不扣款 |
| **步骤跳跃** | 用户先付款再发货 | 直接调发货接口 |
| **时间窗口** | 验证码 5 分钟有效 | 暴力破解 |

**LLM 缺陷**：LLM 不理解时序。它看到 paymentService.pay() 和 orderService.ship() 不会想到「这两个操作之间有没有竞态条件」。

### 2.4 隐式信任型

**本质**：代码信任了一个不应该信任的数据源。

| 子类型 | 隐式信任 | 攻击 |
|--------|---------|------|
| **客户端计算** | 前端算总价 | 篡改总价 |
| **客户端状态** | 前端传步骤编号 | 跳过步骤 |
| **第三方回调** | 支付回调不验签 | 伪造支付成功 |

**LLM 缺陷**：LLM 不知道「总价应该由后端计算」——这是业务常识，不是代码规则。

## 三、业务逻辑分析的三层认知

| 认知层次 | 描述 | LLM 能力 |
|---------|------|---------|
| **L1 模式匹配** | 识别已知的业务逻辑漏洞模式（IDOR、状态机绕过） | ⚠️ 部分能做 |
| **L2 业务理解** | 理解这个系统的业务流程，然后判断代码是否偏离 | ❌ 几乎不能做 |
| **L3 业务推理** | 从代码反推业务规则，然后发现规则之间的矛盾 | ❌ 完全不能做 |

**当前实现的 FWD-C 停留在 L1。** 它加载 types/业务逻辑/ 下的模式文件（IDOR、支付绕过、状态机绕过），然后匹配代码。但这只能发现**已知模式**的漏洞。

**真正的业务逻辑漏洞发现需要 L2 甚至 L3。** 你需要：
1. 先理解这个系统的业务流程（订单流程、支付流程、审批流程）
2. 然后看代码是否偏离了业务流程
3. 或者从代码反推业务规则，然后发现规则之间的矛盾

## 四、如何教 LLM 做业务逻辑分析

### 4.1 先建立业务模型，再审计代码

**当前做法**（错误）：直接从代码开始审计，遇到业务逻辑问题时才去理解业务。

**正确做法**：

`
Phase 0: 业务建模（在代码审计之前）
  ↓
Phase 1: 从文档中提取业务流程
  ↓
Phase 2: 从代码中验证业务流程
  ↓
Phase 3: 发现偏离
`

**具体步骤**：

1. **读取所有文档**（doc/ 下的业务需求、用户手册、API 文档）
2. **提取业务实体**：订单、用户、商品、支付、审批...
3. **提取业务流程**：下单 → 付款 → 发货 → 收货 → 评价
4. **提取业务规则**：
   - 用户只能操作自己的订单
   - 付款后才能发货
   - 库存不足不能下单
   - 优惠券不能叠加使用
5. **生成业务模型文件**：projects/{groupId}/business-model.md

### 4.2 FWD-C 的正确工作方式

**当前做法**（java-forward-vuln-discovery/SKILL.md）：

`
FWD-C：加载 types/业务逻辑/ → 每节点过 D3（业务规则强制） → 终止：业务流结束
`

这太模糊了。「业务规则强制」是什么意思？怎么判断？

**正确做法**：

`
FWD-C 工作流：
1. 加载 projects/{groupId}/business-model.md
2. 对每个端点，确定它属于哪个业务流程的哪个步骤
3. 检查该步骤的业务规则是否被代码实现：
   a. 归属校验：是否检查了对象归属？
   b. 状态校验：是否检查了前置状态？
   c. 数量校验：是否校验了数量合理性？
   d. 权限校验：是否检查了操作权限？
   e. 并发控制：是否有锁或事务？
4. 如果某个规则缺失 → 报漏洞
5. 如果某个规则存在但实现有误 → 报漏洞
`

### 4.3 业务逻辑漏洞的报告格式

**当前问题**：FWD-C 的报告格式和 FWD-A 一样（finding JSON），但业务逻辑漏洞没有 sink，无法用同样的格式。

**正确格式**：

`json
{
  "type": "BUSINESS_LOGIC",
  "subtype": "missing_ownership_check",
  "business_rule": "用户只能操作自己的订单",
  "rule_source": "doc/order-spec.md#3.2",
  "endpoint": "POST /api/orders/{id}/cancel",
  "code_location": "OrderController.java:45",
  "missing_check": "order.getUserId() == currentUser.getId()",
  "attack_scenario": "攻击者替换 orderId 为他人的订单 ID，可以取消他人的订单",
  "impact": "IDOR - 水平越权",
  "severity": "严重"
}
`

## 五、当前实现的批判

### 5.1 types/业务逻辑/ 的问题

当前有 5 个业务逻辑类型文件：IDOR、批量赋值、支付绕过、状态机绕过、越权访问。

**问题**：这些是**通用模式**，不是**项目特定的业务规则**。LLM 可以用这些模式做 L1 级别的匹配，但无法做 L2 级别的业务理解。

**改进**：
- 保留 types/业务逻辑/ 作为通用模式库
- 新增 projects/{groupId}/business-rules.md 存放项目特定的业务规则
- FWD-C 启动时同时加载两者

### 5.2 FWD-C 的问题

FWD-C 的判定逻辑「每节点过 D3（业务规则强制）」太模糊。

**改进**：D3 应该是一个具体的检查清单：
- [ ] 归属校验
- [ ] 状态校验
- [ ] 数量校验
- [ ] 权限校验
- [ ] 并发控制
- [ ] 频率限制

### 5.3 缺少业务建模阶段

当前 Phase 1 是「文档与环境识别」，但没有明确要求提取业务模型。

**改进**：Phase 1 必须产出 projects/{groupId}/business-model.md，包含：
- 业务实体清单
- 业务流程图
- 业务规则清单

---

## 六、一句话总结

**业务逻辑漏洞没有 sink。它存在于代码和业务规则之间的缝隙里。要发现它，你必须先理解业务应该怎么做，然后才能发现代码偏离了什么。这不是搜索问题，而是理解问题。LLM 做不好理解，因为它没有业务上下文——除非你主动给它。**
