# 乔布斯：产品哲学分析

> 方法：从用户体验和产品思维出发。不是问「能做什么」，而是问「应该做什么」。
> 核心理念：简洁是终极的精致。说「不」比说「是」更重要。

---

## 一、这个产品的问题

### 1.1 它太复杂了

> "Simple can be harder than complex. You have to work hard to get your thinking clean to make it simple."

当前 AgentLoop 的问题：**它试图做所有事情。**

6 个阶段、7 篇必读、4 种 FWD 模式、5 个评分维度、15+ 引用文件、12 个报告模板。

这不是产品。这是**功能堆砌**。

乔布斯会问：**如果只能做一件事，你做什么？**

答案是：**发现漏洞。**

不是威胁建模、不是 Filter 分析、不是端点枚举、不是评分机制、不是自优化循环。

就是**发现漏洞**。其他一切都是为这个目标服务的。如果某个功能不直接服务于「发现漏洞」，就应该删除。

### 1.2 它不知道用户是谁

> "You've got to start with the customer experience and work backwards to the technology."

当前 AgentLoop 的用户是谁？

- 安全审计员？→ 他们需要准确的漏洞报告
- 开发者？→ 他们需要可操作的修复建议
- 项目经理？→ 他们需要风险概览
- AI Agent？→ 它需要清晰的执行指令

**问题是：它试图同时服务所有用户，结果谁都没服务好。**

安全审计员觉得报告不够深入。开发者觉得没有修复建议。项目经理觉得报告太技术化。AI Agent 觉得指令太复杂。

乔布斯会说：**选一个用户。只服务他。把他服务到极致。**

建议用户：**安全审计员**。因为原始需求说「不需要修复建议，本 loop 只专注漏洞发现」。

### 1.3 它没有灵魂

> "Design is not just what it looks like and feels like. Design is how it works."

当前 AgentLoop 的灵魂是什么？

**没有。** 它是一堆规则的集合，没有统一的设计哲学。

有些规则来自用户的历史经验（假阳反例库），有些来自 AI 的建议（三哲学自检模板），有些来自行业惯例（STRIDE 矩阵）。

这些规则没有统一的设计语言。它们被拼接在一起，像弗兰肯斯坦的怪物。

乔布斯会说：**找到一个核心原则。让所有设计都从这个原则推导出来。**

## 二、产品定位：从「瑞士军刀」到「手术刀」

### 2.1 当前定位：瑞士军刀

AgentLoop 试图成为一把瑞士军刀——什么都能做一点，但什么都不精通。

| 功能 | 质量 |
|------|------|
| 威胁建模 | 平庸（填 STRIDE 矩阵） |
| Filter 分析 | 平庸（列出 Filter 链） |
| 端点枚举 | 好（codegraph 辅助） |
| 漏洞发现 | 好（但有假阳问题） |
| PoC 验证 | 平庸（环境依赖大） |
| 报告生成 | 好（但太长） |
| 自优化 | 差（没有持久化） |

### 2.2 正确定位：手术刀

AgentLoop 应该成为一把手术刀——只做一件事，但做到极致。

**那一件事是：从 Java 源代码中发现安全漏洞。**

不建模、不分析 Filter、不枚举端点、不验证 PoC、不生成报告、不自优化。

这些功能可以作为**插件**存在，但不是核心。

核心是：**给 AI 一条调用链，AI 告诉你它是否安全。**

### 2.3 手术刀的设计

**输入**：一条 source → sink 的调用链（标注了消毒器）

**输出**：
`json
{
  "verdict": "vulnerable" | "safe" | "uncertain",
  "confidence": 0.95,
  "reasoning": "...",
  "evidence": ["file:line", "..."],
  "severity": "critical" | "high" | "medium" | "low",
  "attack_scenario": "..."
}
`

**就这么多。** 没有 Phase、没有 Skill、没有评分。

其他所有功能（威胁建模、端点枚举、报告生成）都是围绕这个核心的**辅助工具**。

## 三、用户体验：从「命令 AI」到「与 AI 对话」

### 3.1 当前体验：命令 AI

用户当前的体验是：

1. 写一大段指令（启动 loop、加载 Skill、配置参数）
2. 等 7 小时
3. 收到一堆报告
4. 人工复核

这是**批处理模式**——用户提交任务，等结果。

问题：
- 7 小时太长了。用户不知道 AI 在做什么。
- 报告太多了。用户不知道先看哪个。
- 没有交互。用户不能中途调整方向。

### 3.2 正确体验：与 AI 对话

更好的体验是：

1. 用户说：「审计这个项目」
2. AI 说：「我发现了 23 个高风险端点。要先看哪个？」
3. 用户说：「看支付相关的」
4. AI 说：「支付模块有 3 个端点。端点 A 有一条可疑调用链：[source] → [transform] → [sink]。消毒器 X 在这里，但它在拼接之后才调用，所以无效。这是一个 SQL 注入漏洞。要看详细分析吗？」
5. 用户说：「看」
6. AI 展示详细分析
7. 用户说：「继续看下一个」

这是**对话模式**——用户和 AI 实时交互。

优势：
- 用户可以随时调整方向
- 用户可以深入感兴趣的部分
- 用户不需要等 7 小时

### 3.3 对话模式的技术实现

**前提**：预计算所有 source → sink 路径（用工具，不用 LLM）

**流程**：
1. 工具层预计算所有路径（10min）
2. AI 按风险排序，展示 Top 10
3. 用户选择要深入分析的路径
4. AI 逐条分析，展示结果
5. 用户决定是否继续

**优势**：
- 用户 10 分钟后就能看到第一批结果（而不是 7 小时）
- 用户可以聚焦最重要的路径（而不是全量分析）
- 用户可以随时停止（而不是必须跑完整个 loop）

## 四、产品原则：从 AgentLoop 学到的

### 4.1 原则 1：说「不」

> "Innovation is not about saying yes to everything. It's about saying no to all but the most crucial features."

当前 AgentLoop 说了太多「是」：
- 是的，我们要威胁建模
- 是的，我们要 Filter 分析
- 是的，我们要 4 种 FWD 模式
- 是的，我们要评分机制
- 是的，我们要自优化循环

**应该说「不」的**：
- 不，我们不做威胁建模（用工具自动推断）
- 不，我们不做 Filter 分析（合并到路径分析中）
- 不，我们不做 4 种 FWD 模式（合并为 1 个任务）
- 不，我们不做评分机制（用人工抽样验证质量）
- 不，我们不做自优化循环（用持久化机制替代）

### 4.2 原则 2：隐藏复杂性

> "The user doesn't need to know how the engine works. They just need to drive the car."

当前 AgentLoop 暴露了太多复杂性：
- 用户需要知道 6 个阶段
- 用户需要知道 7 篇必读
- 用户需要知道 4 种 FWD 模式
- 用户需要知道 Memurai 缓存策略

**应该隐藏的**：
- 用户只需要说「审计这个项目」
- AI 自己决定怎么做
- 用户只看到结果

### 4.3 原则 3：结果先行

> "People don't want to buy a quarter-inch drill. They want a quarter-inch hole."

用户不想买「6 阶段审计流程」。用户想要「漏洞列表」。

当前 AgentLoop 的产出：
- 威胁模型报告
- Filter 分析报告
- 端点清单
- 调用链分析报告（每个端点一个）
- PoC 报告
- 反思报告
- 评分报告

**用户真正想要的**：
- 漏洞列表（按严重程度排序）
- 每个漏洞的证据
- 每个漏洞的攻击场景

其他报告可以作为**详细信息的入口**，但不是主要产出。

### 4.4 原则 4：体验是连续的

> "The experience should feel like a single, coherent story, not a collection of disconnected features."

当前 AgentLoop 的体验是断裂的：
- Phase 1 产出文档 → Phase 2 产出威胁模型 → Phase 3 产出 Filter 分析 → ...
- 每个阶段的产出是独立的文件，没有统一的入口
- 用户需要自己拼凑这些信息

**应该的体验**：
- 一个统一的入口（如一个 Dashboard）
- 从入口可以看到所有信息
- 信息之间有清晰的关联（如点击漏洞可以跳到调用链分析）

## 五、原子需求的产品化

### 5.1 原子需求 1：枚举 source → sink 路径

**产品化**：这不是用户关心的。用户不关心「枚举路径」，用户关心「哪些地方可能有漏洞」。

**行动**：把这个需求隐藏在工具层。用户不需要知道它存在。

### 5.2 原子需求 2：判断路径安全性

**产品化**：这是核心价值。用户关心的就是「这条路径安不安全」。

**行动**：把这个需求做成核心功能。AI 的判断结果就是产品的核心输出。

### 5.3 原子需求 3：验证漏洞

**产品化**：这是增值功能。用户关心「这个漏洞是不是真的」。

**行动**：作为可选功能。用户可以要求 AI 验证某个漏洞，但不强制。

### 5.4 原子需求 4：生成报告

**产品化**：这是交付物。用户最终需要一份报告。

**行动**：报告应该简洁、结果先行、人类可读。不超过 3 页。

### 5.5 原子需求 5：知识沉淀

**产品化**：这不是用户关心的。用户不关心「知识沉淀」，用户关心「下次审计更快」。

**行动**：隐藏在系统内部。用户只需要感受到「AI 越来越聪明」。

## 六、乔布斯式改进建议

### 6.1 重新定义产品

**当前定义**：Java 代码白盒安全审计 Agent Loop

**正确定义**：Java 安全漏洞发现器

**区别**：
- 「Agent Loop」是技术术语，用户不关心
- 「漏洞发现器」是用户语言，用户一听就懂

### 6.2 简化界面

**当前界面**：命令行 + 一堆 Markdown 文件

**正确界面**：

`
$ audit /path/to/project

扫描中... (10min)

发现 23 个高风险端点，47 条可疑调用链。

Top 5 风险：
1. [致命] SQL 注入 - UserController.search() → UserDao.query()
2. [严重] RCE - FileController.upload() → Runtime.exec()
3. [严重] IDOR - OrderController.cancel() → 缺少归属校验
4. [高] XSS - CommentController.post() → response.write()
5. [高] 路径遍历 - FileController.download() → new File(path)

要看详细分析吗？输入编号：
`

### 6.3 删除功能

**应该删除的**：
1. 威胁建模（Phase 2）→ 用工具自动推断
2. Filter 分析（Phase 3）→ 合并到路径分析中
3. 4 种 FWD 模式 → 合并为 1 个任务
4. 评分机制 → 用人工抽样验证
5. 三哲学自检 → 删除（这是给人看的，不是给 AI 执行的）
6. 12 个报告模板 → 合并为 1 个

**应该保留的**：
1. 路径枚举（用工具自动化）
2. 路径安全性判断（LLM 核心任务）
3. PoC 验证（可选，按需）
4. 报告生成（简洁，结果先行）
5. 知识沉淀（隐藏在内部）

### 6.4 一句话总结

> **不要做一个什么都能做的工具。做一个只做一件事、但做到极致的工具。那件事是：从 Java 代码中发现漏洞。其他一切都是噪音。**

## 七、乔布斯会怎么做？

如果乔布斯来做这个项目，他会：

1. **第一天**：把所有文件读一遍。然后删掉 80%。
2. **第二天**：写一个最简单的原型——用 codegraph 提取 10 条调用链，让 LLM 判断安全性。
3. **第三天**：拿给安全审计员用。看他们的反应。
4. **第四天**：根据反馈迭代。
5. **第五天**：发布。

他不会花 3 个月写 15 个文档。他会花 1 周做一个最小可行产品，然后迭代。

> "Real artists ship."
