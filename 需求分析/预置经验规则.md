# AgentLoop 预置经验规则

> 从 390 个 OpenCode session、约 2259 条 user 消息中提炼的**大模型天生缺失的审计经验**
> 这些规则不是「知识」，而是「实战教训」——LLM 不会因为训练数据就知道这些
> 生成时间：2026-06-13

---

## 一、污点分析实战规则（LLM 最容易犯的错）

### 1.1 Sink 点存在 ≠ 漏洞（最高频错误）

**问题**：LLM 看到 Runtime.exec()、JdbcTemplate.query() 就报漏洞，不追溯参数来源。

**规则**：
- 必须 LSP/Codegraph 回溯确认参数可控
- 必须验证 source → sink 路径上无有效消毒
- 必须确认消毒器是否真的有效（不是看到 PreparedStatement 就认为安全）

**反例**：
`java
// LLM 误报：看到 JdbcTemplate.query 就报 SQLi
// 实际：使用了 PreparedStatement + setString，已消毒
jdbcTemplate.query(sql, new Object[]{name}, rowMapper);
`

---

### 1.2 消毒器识别陷阱

**问题**：LLM 看到 PreparedStatement 就认为安全，但不检查是否真的用了参数化。

**规则**：
- PreparedStatement + setString/setInt/setLong = 有效消毒
- PreparedStatement + 字符串拼接 = **无效消毒**（仍然 SQLi）
- 必须检查 setXxx 调用，不能只看 prepareStatement

**反例**：
`java
// LLM 误判为安全
String sql = "SELECT * FROM users WHERE name = '" + name + "'";
PreparedStatement ps = conn.prepareStatement(sql);  // 看起来安全，实际 SQLi
`

---

### 1.3 跨 JAR/三方服务追踪断链

**问题**：LLM 追踪到 JAR 包调用就停了，报「需人工分析」，但没说清楚为什么断链。

**规则**：
- 跨 JAR 调用必须标注「断链原因」（无反编译/无源码/三方服务）
- 如果有 jadx 反编译结果，继续追踪
- 如果是三方服务（HTTP/RPC），标注「需人工确认服务实现」
- 断链点必须记录到报告，供人工复核

---

### 1.4 参数传递深度限制

**问题**：LLM 无限追踪参数传递，消耗 token 但无新发现。

**规则**：
- 最多追踪 10 层调用
- 每层必须检查「参数是否被强校验」
- 如果发现强校验（如正则白名单、枚举校验），立即标注「已消毒」并降低风险等级
- 如果无法判断是否存在风险，标注「需 AI 介入分析」

---

### 1.5 剪枝时机（何时停止追踪）

**问题**：LLM 不知道何时停止，追踪到无参数方法或数字参数方法。

**L1 端点级剪枝**（不分析）：
- 无参数的 GET 方法
- 参数全为数字类型（int/long/Integer/Long）
- 返回静态资源（图片、CSS、JS）

**L2 链级剪枝**（每层消毒检查）：
- 参数被正则白名单校验
- 参数被枚举校验
- 参数被 Integer.parseInt 等强类型转换
- 参数被 StringUtils.isBlank 等空值检查后直接返回

**L3 跨轮次剪枝**（避免重复）：
- 上一轮已分析过的方法，本轮跳过
- 上一轮已确认为安全的方法，本轮不再追踪

## 二、工具使用经验（LLM 不知道的最佳实践）

### 2.1 Codegraph vs LSP vs ast-grep 选择

**问题**：LLM 不知道何时用哪个工具，经常混用或错用。

**规则**：
- **Codegraph**：查调用关系、查类继承、查注解（SQL 查询）
- **LSP**：查方法定义、查引用、查类型（精确但慢）
- **ast-grep**：查代码模式、查语法树（快但需要写 pattern）
- **grep/rg**：查字符串、查配置（最快但最不准）

**优先级**：
- 查调用链：Codegraph > LSP > ast-grep > grep
- 查代码模式：ast-grep > grep > LSP
- 查配置：grep > Codegraph > LSP

---

### 2.2 Codegraph 初始化检查

**问题**：LLM 每次启动都执行 codegraph init，浪费时间。

**规则**：
- 启动前检查 codegraph.db 是否存在
- 检查 codegraph.db 的 mtime 是否早于源码最新修改
- 如果已存在且未过期，跳过初始化
- 如果源码有变更，执行 codegraph index 增量更新

**脚本**：
`python
import os, time
db_path = f"{project_root}/.codegraph/codegraph.db"
if os.path.exists(db_path):
    db_mtime = os.path.getmtime(db_path)
    # 检查源码是否有更新
    src_mtime = max(os.path.getmtime(f) for f in glob.glob(f"{project_root}/**/*.java", recursive=True))
    if db_mtime > src_mtime:
        print("Codegraph 已存在且未过期，跳过初始化")
    else:
        run("codegraph index")
else:
    run("codegraph init && codegraph index")
`

---

### 2.3 Memurai/Redis 缓存策略

**问题**：LLM 不知道哪些数据该缓存，导致重复读取文件。

**规则**：
- **缓存**：方法体、调用链、注解信息、Filter 链
- **不缓存**：大文件内容、临时分析结果
- **TTL**：方法体 24h，调用链 1h，注解 7d
- **Key 设计**：{groupId}:{type}:{fqn}，如 com.example:method:com.example.UserService.getUser

**批预取**：
- 启动时预取所有 Controller 的方法体
- 进入 Phase 5 前预取所有 sink 点的方法体
- 用 memurai-cli MGET 批量读取，减少 IO

---

### 2.4 jadx 反编译检查

**问题**：LLM 不知道 JAR 包是否需要反编译，每次都反编译。

**规则**：
- 检查项目根目录是否有 src/main/java
- 如果有，说明是源码，跳过反编译
- 如果没有，检查是否有 .jar 文件
- 如果有 JAR，执行 jadx 反编译到 src/main/java
- 反编译后执行 codegraph index

**脚本**：
`python
if not os.path.exists(f"{project_root}/src/main/java"):
    jars = glob.glob(f"{project_root}/**/*.jar", recursive=True)
    if jars:
        for jar in jars:
            run(f"jadx -d {project_root}/src/main/java {jar}")
        run("codegraph index")
`

## 三、Filter/拦截器分析规则（LLM 最容易漏的）

### 3.1 Filter 链顺序分析

**问题**：LLM 只分析单个 Filter，不考虑 Filter 链的顺序和覆盖关系。

**规则**：
- 必须读取 web.xml 或 @Order 注解，确定 Filter 执行顺序
- 如果 Filter1 存在漏洞，但 Filter2 会拦截请求，风险等级降为「提示」
- 如果 Filter1 和 Filter2 都放行，风险等级保持「严重」
- 必须标注 Filter 链的完整执行路径

**反例**：
`java
// LLM 误报：Filter1 存在 SQLi
// 实际：Filter2 会拦截所有未认证请求，Filter1 不可达
@Order(1) public class AuthFilter { ... }  // 先执行
@Order(2) public class SqlInjectionFilter { ... }  // 后执行，但请求已被拦截
`

---

### 3.2 全局 Filter vs 方法级注解

**问题**：LLM 只看方法级注解（如 @PreAuthorize），不看全局 Filter。

**规则**：
- 必须先分析全局 Filter 链（SecurityFilterChain、web.xml）
- 再分析方法级注解（@PreAuthorize、@Secured）
- 如果全局 Filter 已覆盖，方法级注解是「增强」而非「必须」
- 如果全局 Filter 未覆盖，方法级注解是「必须」

---

### 3.3 Spring Security 配置审计

**问题**：LLM 不检查 SecurityFilterChain 配置，直接认为 Spring Security 已启用。

**规则**：
- 必须检查是否有自定义 SecurityFilterChain Bean
- 如果有，分析其配置（哪些路径放行、哪些路径拦截）
- 如果没有，使用 Spring Security 默认配置（CSRF 启用、Session 启用）
- 必须检查 csrf().disable()、sessionManagement().disable() 等危险配置

**反例**：
`java
// LLM 误判：认为 Spring Security 已启用，CSRF 已防护
// 实际：csrf().disable()，CSRF 未防护
@Bean
public SecurityFilterChain filterChain(HttpSecurity http) throws Exception {
    http.csrf().disable();  // 危险配置
    return http.build();
}
`

## 四、业务逻辑漏洞规则（LLM 最不懂的）

### 4.1 认证协议审计（CAS/OAuth2/SAML）

**问题**：LLM 不懂业务，不检查认证协议的安全风险。

**规则**：
- 识别项目使用的认证协议（CAS、OAuth2、SAML、LDAP）
- 针对每种协议，检查特定安全风险：
  - **CAS**：ticket 验证、replay 攻击、ticket 泄露
  - **OAuth2**：redirect_uri 校验、state 参数、token 泄露
  - **SAML**：签名验证、replay 攻击、XML 注入
  - **LDAP**：注入、匿名绑定、凭证泄露
- 必须理解业务逻辑，再判断逻辑是否存在漏洞

**反例**：
`java
// LLM 漏报：OAuth2 redirect_uri 未校验
// 实际：可以构造恶意 redirect_uri，窃取 token
@RequestMapping("/oauth/callback")
public String callback(@RequestParam String code, @RequestParam String redirect_uri) {
    // 未校验 redirect_uri，可以重定向到恶意网站
    return "redirect:" + redirect_uri + "?code=" + code;
}
`

---

### 4.2 密码算法审计

**问题**：LLM 不检查密码算法的安全性。

**规则**：
- 识别项目使用的密码算法（MD5、SHA1、SHA256、bcrypt、scrypt）
- 如果是 MD5/SHA1，标注「弱算法，易碰撞」
- 如果是 SHA256，检查是否加盐
- 如果是 bcrypt/scrypt，检查 cost factor 是否足够（≥10）
- 必须检查密码存储方式（明文、加密、哈希）

---

### 4.3 会话管理审计

**问题**：LLM 不检查会话管理的安全性。

**规则**：
- 检查 Session ID 生成方式（是否随机、是否可预测）
- 检查 Session 过期时间（是否过长）
- 检查 Session 固定攻击防护（登录后是否重新生成 Session ID）
- 检查 Session 劫持防护（是否绑定 IP/User-Agent）

---

## 五、WAF 识别与绕过规则（LLM 不知道的）

### 5.1 WAF 早期识别

**问题**：LLM 在 Phase 5 才发现 WAF，导致前面分析的路径都被拦截。

**规则**：
- Phase 1 就要识别 WAF（检查 Nginx 配置、ModSecurity、云 WAF）
- 如果识别到 WAF，提取 WAF 规则（正则、黑名单）
- 在 Phase 5 分析时，直接跳过被 WAF 有效拦截的路径
- 如果判断 WAF 可绕过，仍然报问题，但标注「需绕过 WAF」

**反例**：
`
# LLM 误报：SQLi 漏洞
# 实际：WAF 拦截了所有包含 SELECT/UNION 的请求
# 但如果使用编码绕过（如 %53ELECT），WAF 失效
`

---

### 5.2 WAF 绕过检测

**问题**：LLM 不知道 WAF 可以绕过，直接认为安全。

**规则**：
- 如果 WAF 使用正则黑名单，检查是否有绕过方式（编码、大小写、注释）
- 如果 WAF 使用白名单，检查是否有漏网之鱼
- 如果 WAF 可绕过，风险等级保持「严重」，但标注「需绕过 WAF」
- 如果 WAF 不可绕过，风险等级降为「提示」，标注「WAF 已拦截」

---

## 六、报告质量规则（LLM 最容易忽略的）

### 6.1 数据对账

**问题**：LLM 报告的数据不一致，如「发现 100 个端点」但只分析了 80 个。

**规则**：
- 必须对账以下数据：
  - 端点总数 vs 已分析端点数
  - 调用链总数 vs 已分析调用链数
  - Sink 点总数 vs 已分析 sink 点数
  - 漏洞总数 vs PoC 验证数
- 如果对账不一致，标注「数据对账 WARN」
- 如果 WARN 项 > 1，不能结束 loop

---

### 6.2 调用链统计

**问题**：LLM 报告不统计调用链，导致无法评估覆盖率。

**规则**：
- 每个 API 必须统计：
  - 调用链总数
  - 致命/严重/中/低调用链数
  - 已分析调用链数
  - 未分析调用链数（标注原因）
- 如果覆盖率 < 50%，启动逆向污点分析，查找遗漏的路由配置

---

### 6.3 结果先行

**问题**：LLM 报告先写细节，后写结论，人类难以快速定位。

**规则**：
- 报告结构必须是：执行摘要 → 审计 Checklist → 细节 → 绘图
- 执行摘要必须包含：业务说明、关键风险点、防护现状、综合定级
- 审计 Checklist 必须列出已执行的安全检查项
- 细节必须包含调用链图、污点传播分析、sink 点详情、PoC 过程

---

## 七、Agent 执行优化规则（LLM 不会自己优化的）

### 7.1 Subagent 失败处理

**问题**：Subagent 失败后，LLM 不知道是重试还是放弃。

**规则**：
- Subagent 失败 1 次：重试，换 prompt
- Subagent 失败 2 次：分析失败原因，如果是环境问题，降级
- Subagent 失败 3 次：放弃，标注「需人工分析」
- 心跳检测：subagent 1 小时无回复，直接 kill

---

### 7.2 并发度调优

**问题**：LLM 不知道何时并发、何时串行。

**规则**：
- Phase 1-4：串行执行（有依赖）
- Phase 5：并发执行（每个端点独立分析）
- Phase 6：串行执行（汇总需要所有 Phase 5 结果）
- Subagent 并发数：最多 5 个（避免 token 爆炸）

---

### 7.3 缓存命中率提升

**问题**：LLM 重复读取相同数据，浪费 token。

**规则**：
- 方法体读取后缓存到 Memurai，TTL 24h
- 调用链分析后缓存到 Memurai，TTL 1h
- 注解信息缓存到 Memurai，TTL 7d
- 每轮 loop 开始时，检查缓存命中率，如果 < 50%，优化缓存策略

---

## 八、自优化循环规则（LLM 不会自己反思的）

### 8.1 评分维度

**问题**：LLM 不知道如何评分自己的输出。

**规则**：
- 执行过程（30 分）：是否按流程执行、是否有遗漏
- 判断依据（30 分）：是否有证据支撑、是否有推理过程
- 思考全面（30 分）：是否考虑所有分支、是否有遗漏
- 内容准确（10 分）：是否有事实错误、是否有幻觉
- 格式人类友好（附加 10 分）：是否易读、是否有图表

---

### 8.2 收敛条件

**问题**：LLM 不知道何时停止循环。

**规则**：
- 连续 3 轮所有项 > 85 分（即 > 25.5/30 或 > 8.5/10），标记 finished
- 如果任一项 < 27 分（30 分项）或 < 9 分（10 分项），优化后重跑
- 如果连续 5 轮无法收敛，人工介入

---

### 8.3 优化建议沉淀

**问题**：LLM 每轮反思后不保存优化建议，下一轮重复犯错。

**规则**：
- 每轮结束时，将优化建议写入 loop_audit/optimization-suggestions.jsonl
- 下一轮开始时，读取上一轮的优化建议
- 如果优化建议被采纳且有效，沉淀到 行为准则/经验/
- 如果优化建议无效，标注「已验证无效」，避免重复尝试
