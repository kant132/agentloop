# 必读 07：剪枝逻辑硬约束

> **漏掉就完蛋**——不剪枝 = 全量展开 = 1 个端点跑到天荒地老；剪错 = 漏报真实漏洞。
> 本文件是**硬约束**，所有 FWD-X subagent 必读、必执行。

## 一、剪枝的 3 个层面

| 层面 | 触发时机 | 决策 |
|------|---------|------|
| **L1 端点级** | Phase 4 端点枚举后，Phase 5 启动前 | 端点是否值得分析？ |
| **L2 链级** | FWD-X 进入每一层函数时 | 该分支是否继续？ |
| **L3 跨轮次** | 新一轮 Loop 启动时 | 是否重做已 final 的？ |

## 二、L1 端点级剪枝（7 条规则）

### 规则 1：无参数端点
- **条件**：endpoint 无 `@RequestParam` / `@RequestBody` / `@PathVariable` / `@RequestHeader` 参数
- **动作**：跳过分析 → 标 `prune_reason=no_params`
- **记录**：`loop_audit/pruning-log.jsonl` 写一行
- **复审**：人工说"继续"才分析；复审时**只**跑 FWD-C + FWD-D（业务+状态）
- **理由**：无外部输入 = 无注入面

### 规则 2：仅数字参数端点
- **条件**：所有参数类型为 `int` / `long` / `short` / `byte` / `double` / `float` / `boolean` / 枚举
- **动作**：跳过 → 标 `prune_reason=numeric_only`
- **记录**：`loop_audit/pruning-log.jsonl`
- **复审**：人工说"继续"才分析；复审时**只**跑 FWD-C + FWD-D
- **理由**：数字无法做 XSS/SQLi/Command 注入
- **注意**：**业务漏洞仍可能存在**（IDOR、状态机）→ 复审时 FWD-C 仍要跑

### 规则 3：被全局 Filter 拦截的端点
- **条件**：端点路径在 `permitAll()` 白名单**之外**，且 Filter 链覆盖
- **动作**：跳过鉴权分析（FWD-B）但**不**跳过其他
- **记录**：在 endpoint meta 上标 `auth_filter_coverage=full`

### 规则 4：内部接口 + 内网 IP
- **条件**：端点带 `@Inner` / 自定义内部注解 + 部署环境内网 IP 限制
- **动作**：跳过 FWD-A（外部攻击者无法触达）但**不**跳过 FWD-B/C/D
- **记录**：标 `prune_reason=internal_network, fwd_a=skipped`

### 规则 5：健康检查 / 监控
- **条件**：路径含 `/health` / `/actuator/health` / `/metrics` / `/info`
- **动作**：跳过
- **记录**：标 `prune_reason=health_check`

### 规则 6：Swagger / OpenAPI 文档
- **条件**：路径含 `/swagger` / `/v3/api-docs` / `/api-docs`
- **动作**：跳过
- **记录**：标 `prune_reason=api_doc`

### 规则 7：未识别技术的自定义端点
- **条件**：端点带未知自定义注解，且无对应 endpoint 类型映射
- **动作**：标 `needs_human`，**不**自动剪枝
- **记录**：进入 `needs_human` 队列

## 三、L2 链级剪枝（每层函数消毒检查）

**关键**："进入每一层函数都要考虑消毒"——**不是只看终端 sink**。

### 3.1 链上每节点的判定流程

```
对每个节点 N（深度 0 → 20）：
  1. 数据流：上游传给 N 什么值？
  2. N 内部对该值做了什么？
     - 是否调用了消毒器？→ 检查 sanitizer 清单
     - 是否做了类型转换（int / enum）？→ 视为消毒
     - 是否做了白名单校验？→ 视为消毒
     - 是否拼接 / 透传？→ 未消毒
  3. 决策：
     - 已被有效消毒（对当前 sink 类型）→ PRUNE 该分支
     - 未消毒 → 继续向下
     - 不确定 → 不剪枝，标 maybe_sanitized
```

### 3.2 消毒器清单（effective for each sink type）

| 消毒器 | 检测特征 | 对哪些 sink 有效 |
|--------|---------|------------------|
| **PreparedStatement + setXxx** | `prepareStatement` + `setString/setInt/...` | SQLi ✅ |
| **MyBatis #{}** | XML/注解 `#{}` | SQLi ✅ |
| **Hibernate Parameter** | `setParameter` / `:name` + setXxx | SQLi ✅ |
| **HTML Encode** | `HtmlUtils.htmlEscape` / `StringEscapeUtils.escapeHtml` | XSS ✅ |
| **URL Encode** | `URLEncoder.encode` | XSS (URL context) ✅ |
| **Path Normalize** | `Path.normalize` / `FilenameUtils.getName` | 路径遍历 ✅ |
| **白名单** | `Pattern.matches` + 字面量 | 全注入 ✅ |
| **类型转换** | `Integer.parseInt` / `Enum.valueOf` | 全注入 ✅ |
| **JSON Schema 校验** | `JsonSchema.validate` | 反序列化 ✅ |
| **ObjectInputFilter** | `setObjectInputFilter` + 白名单 | 反序列化 ✅ |
| **Jackson PolymorphicTypeValidator** | `BasicPolymorphicTypeValidator` | 反序列化 ✅ |
| **Filename 白名单扩展名** | `endsWith(".jpg")` + 集合 | 文件上传 ✅ |
| **MIME 校验** | `file.getContentType()` + 白名单 | 文件上传 ✅ |
| **域名白名单** | `WHITELIST_DOMAINS.contains(host)` | SSRF ✅ |
| **@PreAuthorize 完整覆盖** | 注解存在 + 表达式正确 | FWD-B 缺失 |

### 3.3 链节点上的剪枝标记

```json
{
  "fqn": "com.example.UserService.findByName",
  "depth": 1,
  "node_type": "service",
  "pruning": {
    "status": "active" | "pruned" | "maybe_pruned",
    "reason": "sanitized_by_PreparedStatement",
    "evidence": "UserDao.java:23 preparedStatement.setString"
  }
}
```

### 3.4 终止条件（任一）

- 命中 sink（FWD-A）
- 节点状态 `pruned`
- 深度 = 20
- 跨入已审计项目（groupId 不同）

## 四、L3 跨轮次剪枝

- 启动新一轮 Loop 前，查 `audit:{gid}:commit:{ch}:finding:{chainId}:final`
- 状态为 `final` → 跳过该 chainId
- 状态为 `draft` → 读取草稿继续评分
- 状态不存在 → 全新分析

## 五、剪枝日志格式

```json
{
  "ts": "2026-06-12T...",
  "level": "L1" | "L2" | "L3",
  "endpoint": "GET /api/users/{id}",
  "chain_id": "...",
  "rule_id": "no_params" | "numeric_only" | "sanitized_by_PreparedStatement" | ...,
  "evidence": "file:line",
  "reversible": true,  // 人工可强制反转
  "fwd_modes_skipped": ["A", "B", "C", "D", "INFO"]
}
```

存到 `loop_audit/pruning-log.jsonl`，每轮汇总统计：
- 各规则命中次数
- 误杀率（人工抽样 30 条）

## 六、误杀率门槛

- 单条规则**误杀率 > 5%** → 立即停用
- 单条规则**命中率 < 70%** → 标记 `low_value`
- 普通 finding 评分门槛 85 / **剪枝规则门槛 90**

## 七、人工复审入口

```bash
# 查看被剪枝的端点
grep '"level":"L1"' loop_audit/pruning-log.jsonl | jq '.'

# 强制重扫某个端点
python 脚本/audit/force-rescan.py --endpoint "GET /api/foo" --modes "C,D"
```

强制重扫时：
- **只跑 FWD-C（业务） + FWD-D（状态）**（来自原始要求）
- 不跑 FWD-A / FWD-B / FWD-INFO（数字/无参数端点无意义）

## 八、与预置规则的关系

预置规则（`rules/07-preset-rules.md`）**加速**剪枝判定：
- 已知 groupId → 不必再 codegraph 查包结构
- 已知框架 → 不必再扫无关注解
- 已知自定义注解 → 直接视为 `@Inner` 等价

**预置规则让剪枝判定更快、更准**。

## 九、报告分桶不变量（P5.4 硬约束）

> **原始指令**：每个外部端点的每个方法都必须输出一篇独立的调用链分析报告

→ 文件分桶到 `loop_audit/routes/{高风险端点,中低险端点}/`，**不变量**：

```
|高风险端点/的 .md 数| + |中低险端点/的 .md 数|  ≡  |外部端点清单条目数|
```

**任何偏差 = 漏报或重复劳动**。

**校验**（Phase 6 必跑）：
```bash
python 脚本/audit/verify-endpoint-coverage.py \
  --endpoints loop_audit/external_endpoints/端点.jsonl \
  --high-risk-dir loop_audit/routes/高风险端点/ \
  --mid-low-risk-dir loop_audit/routes/中低险端点/
```

**文件名规范**（O3 / P5.6，类名中 `.` 写 `__`）：
```
{危险等级}_{全限定类名}_{方法名}_{签名Hash}.md
例：严重_com__example_UserController_search_a1b2c3d4.md
```

**分桶规则**（按调用链最高风险）：
- 致命 / 严重 / 中危 → `高风险端点/`
- 低危 / 无风险 → `中低险端点/`

详见 `rules/05-data-reconcile.md` 第 8 项。
