# 经验 02：假阳反例库

> FWD-X subagent 报的漏洞经人工/环境验证为"非问题"的，归档到反例库，防止重报。

## 一、假阳的来源

| 来源 | 典型场景 | 防御 |
|------|---------|------|
| **消毒器未识别** | 已用 PreparedStatement 但 subagent 没看到 | 完善 sanitizer AST 模式 |
| **鉴权未识别** | 全局 Filter 已覆盖但 subagent 只看方法注解 | 读 Filter 全局链，不只读方法级 |
| **剪枝过度** | 把真实端点剪掉了 | 剪枝误杀率 > 5% 即停用 |
| **类型库缺模式** | 误把内部调用当外部 | 补 `类型/...` 模式 |
| **业务理解错** | LLM 不懂业务，误判 | 加载 `项目/{groupId}/` 业务特例 |

## 二、反例记录格式

```json
{
  "false_positive_id": "fp-2026-06-12-001",
  "fwd_mode": "A",
  "reported_as": "SQL_INJECTION",
  "actual_state": "SANITIZED",
  "chain": "Controller.search → DAO.query",
  "missed_sanitizer": {
    "type": "PreparedStatement",
    "evidence": "DAO.query:23 preparedStatement.setString(1, name)",
    "code_snippet": "..."
  },
  "root_cause": "sanitizer pattern incomplete - missing setString detection",
  "fix_action": "补充 ast-grep 模式：PreparedStatement + setXxx",
  "promoted_to_type": "类型/注入类/SQL注入.md#误报模式"
}
```

存到 `loop_audit/feedback/false-positives.jsonl`。

## 三、模式沉淀

反例累积到 3+ 条同类 → 沉淀到 `类型/{X}.md` 的"误报模式"小节：

```markdown
## 误报模式

### 模式 1：PreparedStatement + setXxx
- 特征：`prepareStatement` 后调用 `setString/setInt/setLong/...`
- 防御：FWD-A 命中此类调用，sanitizer 字段必填 `effective=true`
- 证据类型：方法体含 `setString(数字, 变量)`
```

## 四、自检

每轮 Loop 结束：
- 抽样 20 条 finding 人工复核
- 假阳率 > 10% → 立即停用对应判定规则
- 假阳率 5-10% → 标记 `unstable`
- 假阳率 < 5% → 健康

## 五、必读

- subagent 启动前读 `loop_audit/feedback/false-positives.jsonl`（如存在）
- 命中相似模式 → 标注 `similar_to_fp:{id}` 并降级 confidence
