# 经验 04：性能瓶颈案例

> 来自实战：以下瓶颈场景曾导致 loop 跑 5+ 小时才完成 1 轮。

## 一、瓶颈分类

| 类别 | 典型症状 | 根因 | 解法 |
|------|---------|------|------|
| **codegraph 慢** | 单次查询 5s+ | SQLite 在大表上未建索引 | 索引 + 查询优化 |
| **Memurai 慢** | memurai-cli 调用频繁 / 命中率低 | key 设计不合理 + 单条 subprocess 调用 | 按 groupId+commit 分桶 + 批量 MSET |
| **subagent 慢** | 启动后 30min 无结果 | prompt 过长、链太深 | 拆分 prompt、限制深度 |
| **Token 消耗爆炸** | 1 轮 Loop 50w tokens | 链节点过多、prompt 重复 | 批预取 + 共享链数据 |
| **PoC 慢** | 单 PoC 5min+ | 网络慢、payload 复杂 | payload 模板 + 并发 |

## 二、codegraph 优化

### 2.1 索引
```sql
-- 必建索引
CREATE INDEX idx_method_fqn ON method(fqn);
CREATE INDEX idx_method_class ON method(class);
CREATE INDEX idx_call_edge_caller ON call_edge(caller);
CREATE INDEX idx_call_edge_callee ON call_edge(callee);
CREATE INDEX idx_class_fqn ON class(fqn);
CREATE INDEX idx_class_annotation ON class(annotation);
```

### 2.2 查询优化
- 用 `WHERE` 先过滤，再 `JOIN`
- `LEFT JOIN` 数量控制在 10 内（>10 通常应拆查询）
- `LIKE 'prefix%'` 走索引，`LIKE '%middle%'` 不走

## 三、Memurai 优化（走 memurai-cli.exe）

### 3.1 key 设计
- 必带 `{groupId}:commit:{commitHash}` 前缀 → 避免跨项目污染
- 链方法预取一次 `memurai-cli MSET k1 v1 k2 v2 ...` 多个 → 减少 subprocess 次数
- 批量查询用 `memurai-cli MGET k1 k2 ...` 而非循环 GET

### 3.2 进程级性能
- 每次 `memurai-cli` 调用是子进程（~30ms 启动），**任何场景** 优先 MSET / MGET / Pipeline
- 避免在循环里逐条 `SET` / `GET`
- 大 key（>1MB）改用 stdin 管道传入

### 3.2 TTL 选择
| 数据 | TTL | 理由 |
|------|-----|------|
| method body | 24h | 稳定 |
| chain | 1h | 迭代期短 |
| finding draft | 30 轮 | 防永久滞留 |
| finding final | 永久 | 落盘后保留只读 |
| env reachability | 1h | 环境会变 |

## 四、subagent 优化

### 4.1 prompt 长度
- 单 prompt < 2000 tokens（理想 1000-1500）
- 长 prompt = 启动慢 + 容易失焦
- 拆分：核心指令 + 引用文档（按需 Read）

### 4.2 链深度
- 默认上限 20
- 实际项目 95% 链深度 < 15
- 深度 > 15 极可能是循环 / 框架内部 → 剪枝

### 4.3 并发度
- 4 个 FWD 模式 × 1 subagent = 4 并发（每端点）
- 多端点并行：P0 不超过 3 端点同时（防止 codegraph 争抢）
- 总并发 ≤ 10（受 codegraph + Memurai subprocess 进程数限制）

## 五、Token 优化

| 来源 | 节省手段 |
|------|---------|
| 方法体重复读 | Memurai 预取 |
| 链节点重复传 | Memurai 共享（一次预取 4 个 FWD 共享） |
| prompt 重复发 | 引用文档代替内联 |
| finding 重复分析 | sha256 + 状态查询 |
| finding 落盘 | 3x85 门槛，避免草稿落盘 |
| 类型库重复加载 | subagent 启动时一次性加载 |

## 六、检测

每轮结束统计：
- 总 token 消耗
- 单 finding 平均 token
- 单端点平均耗时
- codegraph 查询次数 / 命中次数
- Memurai 命中率

任一指标恶化 > 30% → 触发优化回路。
