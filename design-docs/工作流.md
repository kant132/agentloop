# 工作流（数据驱动版）

> 所有阶段产物的 JSON 格式定义见 `design-docs/data-schema.md`，本文件不内联 schema。
> 关键约束：`codegraph_db` **必选**；排序维度按**调用链**（不是端点）；方法体缓存在**调用链构建后、AI 分析前**预取到 Memurai。

## 评价指标（仅 6 个）

| 指标 | 定义 | 理想值 |
|------|------|--------|
| chain_method_count | 调用链上的方法体总数 | — |
| loaded_method_count | 实际加载的方法体数 | < chain_method_count × 0.3 |
| vuln_chains | 确认有漏洞的调用链数 | — |
| safe_chains | 确认无漏洞的调用链数 | — |
| unknown_chains | 无法确认的调用链数 | 越少越好 |
| vuln_exposed_surface | 确认有漏洞的暴露面（端点）数 | — |

核心公式：`load_ratio = loaded_method_count / chain_method_count`，理想 < 0.3。其他冗余指标一律删除。字段 schema 见 `data-schema.md` 的 `round_metrics.json` 段。

## 流程（5 阶段 × 数据流）

每阶段只列输入、输出、脚本、引用的 schema 名。漏洞知识、prompt 模板不在本文档。

### Phase 0 — 准备

- 输入：`projects/{group_id}/preset.json`
- 输出：Memurai 清空 `{groupId}:*`，保留 `{groupId}:knowledge:*`
- 脚本：`scripts/audit/check_core_tools.py`，退出码 0 通过，任一工具缺失 exit 2 不降级
- schema：`preset.json`（见 `data-schema.md`，`codegraphDb` 字段标必填）

### Phase 1 — 暴露面采集

- 输入：Java 源码 + preset.json + `codegraph.db`（**必选**）+ SSH 远程目标（可空，缺失则 env_filter 降级）
- 输出：8 份 `exposure/{asset_type}.json` + `exposure_assets.json`（综合去重 + 风险分级，**不排序**）
- 脚本：`python -m scripts.exposure.cli collect` → `synthesize`
- schema：`exposure/{asset_type}.json`、`exposure_assets.json`

> **不排序**：排序维度按调用链，需 `sink_count`，所以排序推后到 Phase 2 调用链构建之后。

### Phase 2 — 调用链 + 缓存 + 排序

顺序固定：**调用链构建 → 链文件落盘 → 方法体缓存（memurai 预取）→ sink 识别 → 调用链优先级排序 → 鉴权类缓存**。

- 输入：`exposure_assets.json` + `codegraph.db`（**必选**）+ `commitHash` + `groupId`
- 输出：
  - `chains/{endpoint}.txt`（链文件）
  - `chain_data.json`（链 + sink_count + priority 队列）
  - Memurai 方法体缓存键 `audit:{groupId}:commit:{commitHash}:method:{fqn}#{sigHash}`（TTL 24h）
  - Memurai 鉴权类缓存键 `{groupId}:auth:class:{fqn}`
- 脚本：
  - `scripts/chain/chain_builder.py`（CTE 递归构建调用链）
  - `scripts/chain/chain_file_writer.py`（链文件落盘）
  - `scripts/redis/redis-batch-prefetch.py` + `memurai_client.py`（**缓存时机**：链构建后、分析前预取）
  - `scripts/chain/sink_registry.py`（预置 80+ sink + 非 groupId 命名空间动态识别）
  - `scripts/chain/priority_calculator.py`（按链维度排序，公式见下）
  - `scripts/chain/auth_class_cacher.py`（鉴权类一次性缓存）
- schema：`chains/{endpoint}.txt`、`chain_data.json`、`method_cache key`、`auth_class_cache key`

排序公式（按链维度）：

```
priority = base + sink_count + preset_sink_matches * 10
```

- `base`：无外部参数 `-100` / POST/PUT/DELETE `10` / GET `0`
- `sink_count`：链上 sink 总数（来自 sink_registry）
- `preset_sink_matches`：命中预置 sink 库的次数

排序必须发生在调用链构建之后（依赖链上 `sink_count`）。同一端点的多条链各链独立计分。

### Phase 3 — AI 分析

- 输入：`chain_data.json`（按 `priority` 队列消费）+ Memurai 方法体缓存（已在 Phase 2 预取）
- 输出：每链一份 `analysis_report.json` + `loads.db`（加载次数追踪）
- 脚本：`scripts/analysis/method_body_loader.py` + `chain_report_generator.py` + `load_counter.py`
- 约束：前 5 层（`depth < 5`）全量加载，第 5 层起按需 `load_by_node_id()`。`load_counter` 记录实际加载方法数，目标 `load_ratio` < 0.3。
- schema：`analysis_report.json`（含 verdict 三态枚举 vuln|safe|unknown）

### Phase 4 — PoC + 收敛

- 输入：`analysis_report.json`
- 输出：`poc_result.json` + `round_metrics.json` + `knowledge.json` + `convergence.json`
- 脚本：`scripts/audit/poc-monitor.py` + `self_evolution.py` + `scripts/analysis/metric_simplifier.py`
- 收敛：`self_evolution.calculate_convergence()` 判定 4-AND（均分 ≥ 85 / 标准差 < 3 / 对账 ≥ 10 / 覆盖率 ≥ 0.95）
- schema：`poc_result.json`、`round_metrics.json`、`knowledge.json`

PoC 三态：`confirmed` / `denied` / `inconclusive`，仅 `confirmed` 计入 `vuln_chains` 与 `vuln_exposed_surface`。
