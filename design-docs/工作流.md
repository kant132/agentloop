# 工作流

本文档描述 agentloop 审计系统的完整执行流程，面向首次接触本项目的工程师与审计员。每个阶段标注目的、输入、输出、涉及脚本与预期结果。硬规则、Scope 边界与常见陷阱不在本文展开，见项目根 `AGENTS.md` 与 `conduct/必读/`。

整个流程分 5 个阶段，依次为：Phase 0 准备、Phase 1 暴露面采集、Phase 2 调用链与 Sink、Phase 3 AI 分析、Phase 4 PoC 验证与收敛。前 4 阶段串行依赖，Phase 3 与 Phase 4 内部存在循环与并发。

## Phase 0 — 准备

**目的**：清理上一轮残留缓存，确认 codegraph / ast-grep / Memurai 三大核心工具就位。任何一项缺失即终止，不降级运行。

**输入**：`projects/{group_id}/preset.json`（含 `projectRoot`、`codegraphDb`、`groupId`、`loopDir`）。

**输出**：Memurai 中 `{groupId}:*` 键全部清空，`{groupId}:knowledge:*` 键保留。`.preflight/status.txt` 写入就绪状态。

**涉及脚本**：`scripts/audit/check_core_tools.py`，退出码即体检结论。

**预期结果**：脚本 exit 0 表示通过。若任一工具缺失，exit 2 并打印缺失清单，审计进程不继续。这一步避免后续阶段因为静默退化产生看似正常但实质失真的结果。

## Phase 1 — 暴露面采集（RFC-0001 新管线）

**目的**：从攻击者与白盒审计双视角，采集 8 类资产并做去重、风险分级与热点排序。

**输入**：Java 项目源码 + `preset.json` + codegraph.db（可选）+ SSH 远程目标（可选）。SSH 缺失时相关 collector 标记为 degraded，不阻塞流程。

**输出**：`{loop_audit_dir}/exposure/*.json`（每个 collector 一个），`_summary.json` 汇总，`exposure_assets.json` 综合产物，`hotspots.json` 取风险前 20%。

**涉及脚本**：调用统一入口 `python -m scripts.exposure.cli collect`，再 `synthesize`，最后 `rank`。

8 个 collector 各管一类资产：

- route：注解路由、XML 路由、程序化注册、Gateway 动态路由
- config：yml/properties/xml 安全相关配置
- codegraph：基于 SQLite 的类与方法关系
- auth_code：鉴权注解、过滤器、拦截器
- sensitive_info：硬编码密钥、Token、连接串
- waf：WAF 资产识别
- db_schema：表结构、敏感字段
- env_filter：环境变量与启动参数过滤

**预期结果**：采集到至少 10 条路由，8 类资产全部覆盖（degraded 标注允许）。热点排序后产出的 `hotspots.json` 是 Phase 2 的主输入。设计细节见 `docs/specs/rfcs/exposure-pipeline-redesign.md`（RFC-0001），本文不展开。

## Phase 2 — 调用链 + Sink + 优先级

**目的**：对每个端点构建调用链，标注潜在 sink，计算优先级队列，决定 AI 分析的入场顺序。

**输入**：Phase 1 的 `hotspots.json` + codegraph.db。

**输出**：每端点一份调用链文件，命名格式 `method:nodeid1->method:nodeid2`；Memurai 中缓存全部方法体；`priority_queue.json` 决定后续消费顺序。

**涉及脚本**：

- `scripts/chain/chain_builder.py`：已有，从 sink 反向回溯到入口
- `scripts/chain/chain_file_writer.py`：新增，按格式落盘
- `scripts/chain/sink_registry.py`：新增，预置 80 个 sink + 动态识别非本 groupId 的外部调用
- `scripts/chain/priority_calculator.py`：新增，按公式计算分值
- `scripts/chain/auth_class_cacher.py`：新增，缓存鉴权类供后续判定

**优先级公式**（RFC-0001 §3.5）：无外部参数的端点 `base = -100` 直接降权；POST/PUT/DELETE `base = 10`；GET `base = 0`。最终分值 = `base + sink_count + preset_match * 10`，其中 `preset_match` 命中预设高危模式则加 10 分。

**预期结果**：调用链总数等于端点总数，高危链排在队列前部，便于 Phase 3 优先消费。

## Phase 3 — AI 分析（按优先级队列）

**目的**：AI 逐链深入分析，前 5 层全量加载方法体，后续按需拉取，产出含污点追踪、业务逻辑、漏洞判定与 CVSS 4.0 评分的详尽报告。

**输入**：优先级队列 + Memurai 缓存的方法体。

**输出**：每链一篇报告，含每个方法体的分析、漏洞根因、PoC 构造方法、payload 草稿、CVSS 4.0 评分。

**涉及脚本**：

- `scripts/analysis/method_body_loader.py`：前 5 层（depth < 5）一次性返回完整方法体，之后只返回 node_id
- `scripts/analysis/load_counter.py`：把每次加载记到 sqlite，用于 Phase 4 的效率评估
- `scripts/analysis/chain_report_generator.py`：组装报告并调用 `estimate_cvss_4`

**加载策略**：前 5 层全量返回，AI 拿到完整上下文。后续层只给 node_id，AI 通过 `load_by_node_id()` 按需拉取。若前 5 层已能确定污点被消除且无业务漏洞，AI 可主动跳过后续层；否则继续加载，AI 自主决定深度。

**预期结果**：高危链产出可复现的漏洞报告，中低危链产出判定结论。所有报告不含修复建议，这是硬约束，违反会被自动判 0 分。

## Phase 4 — PoC 验证 + 收敛

**目的**：基于 Phase 3 报告决定是否启动 PoC 专家，多轮迭代直到收敛判据全部满足。

**输入**：Phase 3 报告 + PoC 环境（可达 / 不可达 / 受限三态）。

**输出**：PoC 报告、`knowledge.json` 经验沉淀、最终评价指标。

**涉及脚本**：

- `scripts/audit/poc-monitor.py`：后台 daemon，轮询 Memurai 队列派发 PoC 任务
- `scripts/audit/self_evolution.py`：收敛 4-AND 判据检查
- `scripts/analysis/metric_simplifier.py`：新增，最终指标 = `loads / cached_count`

**PoC 三态**：是问题（确认漏洞）、非问题（证伪）、暂时无法确认（受环境限制）。三态都写回报告，不强制结论。

**收敛判据**（4-AND 同时满足才终止）：平均分 ≥ 85、标准差 < 3、数据对账通过 ≥ 10 次、端点覆盖率 ≥ 0.95。

**最终效率指标**（RFC-0001 §3.6）：`metric = 方法体实际加载次数 / 缓存的方法体总数`，理想值 < 0.3，表示大部分链看前 5 层即可判定，加载策略有效。

**预期结果**：高危 PoC 通过率达 75% 才允许结束 loop，否则 self-evolution 会触发新一轮采集或重新分析。

## 快速上手

从零启动一次审计的完整命令序列：

```powershell
# 1. 准备 preset.json（复制 projects/_template/ 改填 projectRoot、codegraphDb、groupId）
# 2. 体检 + 清缓存
python scripts/audit/check_core_tools.py
& "C:\Program Files\Memurai\memurai-cli.exe" DEL (memurai-cli KEYS "{groupId}:*" | Where-Object { $_ -notmatch "knowledge:" })

# 3. 启动 daemon
python scripts/audit/cross-agent-50r.py --preset projects/{group_id}/preset.json

# 4. 审计结束后验证端点覆盖不变式
python scripts/audit/verify-endpoint-coverage.py `
  --endpoints {loop_audit_dir}/external_endpoints/端点.jsonl `
  --high-risk-dir {loop_audit_dir}/routes/高风险端点/ `
  --mid-low-risk-dir {loop_audit_dir}/routes/中低险端点/

# 5. 查看效率与覆盖率
python scripts/audit/coverage-audit.py --stats
```

审计产物全部落在 `{loop_audit_dir}` 下，遵循 `|高风险端点| + |中低险端点| ≡ |project-context.json endpoints|` 的不变式。任何偏离表示审计不完整，loop 不会自动终止。
