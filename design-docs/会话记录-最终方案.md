> 本文档基于 2026-06-13 ~ 2026-06-14 的设计评审会话（ses_13e75c168ffe3BJlV80Xqaajlw）汇总整理，按"以最后一次决策为准"原则重建。

> 设计基线：六位大师工程答复 → 32 条 SDD 需求 → 18 条原子需求 → 三层 agent 架构 → Phase↔Layer 映射 → 收敛公式 → Session 压缩 → Memurai 缓存统一。

## 1. 架构设计

### 1.1 三层 Agent 架构

```
[Daemon 层 — cross-agent-50r.py 薄 wrapper]
   │  50 轮循环；每轮清空 groupId 开头缓存；启动 poc-monitor；spawn boss
   ▼
[Boss 层 — java-whitebox-loop skill]
   │  端点枚举、派主管、对账、抽检、评分、收敛判断、拒绝或接受主管结果、自我反思
   │  → 唯一可以修改执行路径、新增脚本、调整流程的角色
   ▼
[Supervisor 层 — endpoint-supervisor skill，每端点一个，并行]
   │  对每条调用链派分析师；按分析师结果决定派哪类专家、按什么顺序；用安审视角质疑
   │  专家若需协调其他专家 → 反馈主管并说明理由；主管漏判则沉淀为普遍性经验
   │  汇总 findings 写 Memurai，向 Boss 汇报
   ▼
[Expert 层 — 5 类挖洞专家 skill]
       - injection-audit / business-logic-audit / file-audit / auth-chain-audit / login-audit
       - call-chain-audit-thinking（分析师，5 维思考，只思考不报漏洞）
       - poc-verify（验证专家，只验证不发现）

[Monitor 层 — poc-monitor.py，独立后台进程]
       轮询 finished 状态的 finding，调度 2 个 poc-verify 并发执行
```

### 1.2 Phase ↔ Layer 映射

| Phase | 内容 | 主执行者 | Layer | 派遣关系 | 产出 |
|------|------|----------|-------|----------|------|
| A | 端点枚举 | Boss | Layer 2 | 无 | `project-context.json` |
| B | 安全上下文 | Boss + ssh-skill 工具 | Layer 2 + 工具 | 无 | `security-context.json` |
| C | 漏洞发现 | Boss → Supervisor → Analyst + Expert | Layer 2 → 3a → 3b+3c | 链式 | findings 写 Memurai |
| D | 自检收敛 | Boss | Layer 2 | 无 | `scoring-history.jsonl` + `convergence.json` |
| PoC | 验证 | Monitor → Verify | Layer 0 → 3d | 独立派遣 | 验证结果回写 Memurai |

**关键约束**：
- Phase A/B/D Boss 独立完成，**不派遣任何 sub-agent**。
- Phase C 全部委托给 Supervisor 链。
- PoC 验证在 Monitor 层独立运行，**不阻塞主流程**。

### 1.3 Memurai 缓存命名空间（已统一）

```
{groupId}:audit:*          ← Boss / Daemon 主命名空间
   ├── {groupId}:audit:security:*      Phase B 安全上下文（filter、sanitizer、SSH 配置）
   ├── {groupId}:audit:finding:{chainId}:draft     专家产出（临时）
   ├── {groupId}:audit:finding:{chainId}:final     待验证（Monitor 轮询）
   ├── {groupId}:audit:finding:{chainId}:verified  已验证
   ├── {groupId}:audit:round:{N}:summary           轮次摘要（Session 压缩用）
   └── {groupId}:audit:scoring:*                   评分历史

{groupId}:sup:*            ← Supervisor 命名空间
   ├── {groupId}:sup:ep:{endpoint}:context    端点上下文
   ├── {groupId}:sup:ep:{endpoint}:analysis   分析师输出
   ├── {groupId}:sup:ep:{endpoint}:dispatch   派遣决策
   ├── {groupId}:sup:ep:{endpoint}:finding    汇总 findings
   ├── {groupId}:sup:ep:{endpoint}:status     主管状态
   ├── {groupId}:sup:ep:{endpoint}:pruning    剪枝记录
   ├── {groupId}:sup:exp:*                    主管经验沉淀（普遍性教训）
   └── {groupId}:sup:ep_status:*              端点审计状态

{groupId}:knowledge:*      ← 跨轮次知识（先写缓存避免文件锁）
```

**每轮清空规则**：Daemon 在 spawn Boss 前执行 `DEL {groupId}:audit:*` 和 `DEL {groupId}:sup:*`，但**保留** `{groupId}:knowledge:*`，由 Boss 在 Phase D 末尾合并到 `knowledge.json`。

### 1.4 Session 历史压缩（三层滑动窗口）

| 范围 | 压缩策略 | 用途 |
|------|---------|------|
| 最近 3 轮 | 保留原始对话 | 本轮内 agent 协调 |
| 3-10 轮前 | 仅保留摘要（≤500 token/轮）| 发现跨轮 pattern |
| 10 轮前 | 仅保留"关键改进"字段 | 已蒸馏到 knowledge.json |

**结构**（写 Memurai `{groupId}:audit:round:{N}:summary`）：
```json
{
  "round": 3,
  "endpoints_count": 47,
  "findings_count": 12,
  "poc_verified_count": 8,
  "key_anomalies": ["..."],
  "key_improvements": ["..."],
  "convergence_judgment": "continue"
}
```

**Token 估算**：未压缩 50 轮 ≈ 2.5M token（必崩）；压缩后 ≈ 154K token（可控）。

### 1.5 收敛公式

**评分对象**（每轮一个总分 0-100）：

```
score = coverage×30% + poc_rate×30% + reconcile×25% + compliance×15%
```

| 维度 | 权重 | 计算 |
|------|------|------|
| 端点覆盖率 | 30% | `实际分析端点数 / 预期端点总数` |
| PoC 验证率 | 30% | `已验证 finding 数 / 需验证 finding 数` |
| 对账 PASS 率 | 25% | `PASS 项数 / 10`（7+1 加上 1 个全局项）|
| 过程合规性 | 15% | Boss 自检清单 PASS 率 |

**收敛条件（4 个 AND）**：
1. 最后 1 轮总分 ≥ 85
2. 最后 3 轮总分**标准差** < 3（不是方差，更直观）
3. 最后 1 轮对账 10 项全 PASS
4. 端点覆盖率 ≥ 95%

**Signal 机制**（替代 stdout 魔法字符串）：Boss 评估满足 4 条件 → 写 `loop_audit/diag/convergence.json` → Daemon wrapper 读文件决定是否 kill ralph-loop。

### 1.6 安全阀

| 安全阀 | 阈值 | 触发者 |
|--------|------|--------|
| 最大轮次 | 50 轮 | Daemon 主循环 |
| 单轮超时 | 3600 秒 | Daemon spawn 子进程 |
| 全局超时 | 180000（用户指定） | Daemon 累计 |
| 端点并行上限 | ulw background 并发数 | Boss 派遣时 |
| 验证并发上限 | 2 个 poc-verify | poc-monitor.py 调度 |

## 2. 需求分析

### 2.1 一句话目标

> **AgentLoop 是一个 SAST 组件，通过形式化的安全审计经验驱动 AI 执行白盒审计，以假阳率为生命线，以知识沉淀为护城河。**

### 2.2 五个根本目标

1. **漏洞准确**：发现的漏洞必须真实可利用，有代码证据链
2. **接口无遗漏**：所有外部暴露的接口都被枚举和分析
3. **调用链无遗漏**：每个接口的每条关键调用链都被遍历
4. **能力充分**：运行高效，能力覆盖到位
5. **知识可沉淀**：跨轮次经验能复用，项目知识能积累

### 2.3 真实痛点（来自 390 session 积累）

| 痛点 | 现象 |
|------|------|
| 假阳率高 | LLM 看到函数名就报漏洞（如 `findById` 直接判 IDOR），或看到 `@PreAuthorize` 就跳 |
| 5 个 FWD subagent 重复跑同一条链 | 浪费 token，结果分散，难对账 |
| 威胁建模只是流程表演 | 真实价值未沉淀，下一轮还得重新做 |
| 三哲学自检（马斯克/康德/苏格拉底）形同虚设 | 没有可验证的 JSON 输出 |
| 工具降级路径导致输出质量不可控 | codegraph 缺失却降级 LSP，结果完全不可信 |
| 评分只看总分不看过程 | 总分高 ≠ 真正做了事 |
| 主管协调出错后没有经验沉淀 | 同样的协调错误反复发生 |

### 2.4 四大差距

| 差距维度 | 现状 | 目标 |
|---------|------|------|
| **架构** | 2 层（daemon → 单体 worker）| 3 层（daemon → boss → supervisor/expert）|
| **流程** | 6 阶段（文档阅读+威胁建模+filter+枚举+挖洞+汇总）| 4 阶段（端点枚举+安全上下文+漏洞发现+对账收敛）|
| **知识** | knowledge.json 偶尔写、靠人工合并 | 自动蒸馏、缓存先行、避免文件锁 |
| **质量** | 文件计数 + 总分 | 覆盖率/PoC 验证率/对账/合规 四维评分 + 4 个 AND 收敛条件 |

### 2.5 优先级矩阵

| 优先级 | 条数 | 累计工时 |
|--------|------|----------|
| **P0** | 16 | 阻塞发布 |
| **P1** | 12 | 核心体验 |
| **P2** | 5 | 锦上添花 |
| **合计** | **33** | — |

最终精炼为 18 条**原子需求**（见第 3 节）。

### 2.6 32→18 映射说明

33 条需求 → 18 条原子需求，"消失"的 15 条去向：

| 类别 | 条数 | 去向 |
|------|------|------|
| 信息密度优化（SKILL ≤50 行、rules ≤3 文件等）| 4 | 由 skill-maintainer agent 独立维护 |
| 工具层自动化细节（codegraph init、技术栈识别等）| 3 | 已隐含在 Phase A 轻装 |
| PoC 后台 monitor 细节 | 2 | 已包含在需求 #3 解耦 |
| 报告模板简化 | 2 | 模板在 skills 中，由 skill agent 维护 |
| 派生需求 | 3 | 派生于 18 条原子需求 |
| 风险/合规性条目 | 1 | 整合进合规性自检 |

## 5. Agent Team 设计

### 5.1 总约束（高于任何角色）

- **每轮 agentloop 启动时清空 groupId 开头的 Memurai 缓存**，跨轮次持久化只走 `knowledge.json`。
- 所有 knowledge 优先写入 `{groupId}:knowledge:*` 缓存，后续 Boss 负责取出来，生成 `knowledge.json`（避免文件锁）。
- 所有决策过程都要有**客观依据**，并一句话说明。
- 主管需要根据专家的反馈沉淀知识和经验教训，分类两类：**普遍性** vs **项目特有**。
- **只有老板可以修改执行路径**，修改 agentloop 工具的流程、增加脚本等，所有修改操作由老板**单独派一个临时工具子 agent** 去实现，避免主流程被污染，且修改必须具有普遍性、不能对当前项目过拟合。

### 5.2 老板（主 agent）`skills/java-whitebox-loop`

**职责**：流程编排、结果评审、反思
- 端点枚举、对账、抽检、评分、收敛判断
- 拒绝或接受主管提交的结果
- 自我反思形成经验
- **可以拒绝主管提交的结果**，指出他的不足、告诉他反思修改后继续执行
- **老板也需要反思自己**，形成经验
- 需求明确、验收标准明确

### 5.3 主管（每端点一个决策 agent）

**职责**：决策、评价、协调
- 老板为每个待审计端点派 1 个主管
- 主管拿到端点通过分析师遍历调用链
- 每条调用链决定要派哪些专家、派几次、按什么顺序
- 专家产出的结果用**安审视角（Chris Anley / 吴翰清 / 尹毅）**质疑
- 不满意就拒回重做
- 专家执行中若认为需其他专家协作，先回主管**说明理由**
- 主管决策后记录这次协调判断：若确实是主管之前漏判，**沉淀为普遍性经验**供后续主管自我修正
- 主管在 experts 全部结束后汇总该端点的 findings，更新缓存状态，向老板汇报
- 决策路径明确、协调分工无差错

### 5.4 分析师（调用链分析 agent）`skills/call-chain-audit-thinking`

**职责**：只思考，不报漏洞
- 给定一条调用链，输出 5 维思考：
  - **入参溯源**：参数是否可被外部控制
  - **消毒验证**：消毒函数调用方式是否正确
  - **权限归属**：操作者是否有权访问该资源
  - **分支绕过**：条件分支是否存在可被攻击者利用的绕过路径（无参数、缺条件检查、catch 吞异常、负值/边界值）
  - **信息泄露**：敏感数据是否暴露给非授权方
- 只输出结构化分析结果，由主管决定后续派哪些挖洞专家

### 5.5 挖洞专家（5 类，各单一职责）

| `skills/file-audit` | 上传 / 下载 / 读取 / 删除 / 临时文件 / 压缩包 / 路径穿越 |

| `skills/login-audit` | 凭证处理 / 暴力破解 / 会话劫持 / MFA 绕过 |

### 5.6 验证专家（PoC 验证 agent）`skills/poc-verify`

**职责**：只验证，不发现
- 主管在 finding 标记 `finished` 后，由 Monitor 派遣
- 执行路径 A(curl)→B(arthas)→C(SSH 后端)
- 产出：环境快照 + 执行记录 + CVSS 3.1 评分 + 最终结论（是问题 / 非问题 / 暂时无法确认）
- 后台 monitor 进程从缓存持续读取 finished 状态的调用链，调度 2 个验证专家并发执行，结果回写缓存供主管读取

### 5.7 Monitor（独立后台进程）`scripts/audit/poc-monitor.py`

## 8. 数据对账机制

每轮 Phase D 末尾执行 **7+1 项对账**：

| # | 项 | 检查方法 |
|---|----|----------|
| 1 | 端点枚举数 == project-context.json 中端点数 | 文本对比 |
| 2 | 每端点有 supervisor 派遣记录 | Memurai 键扫描 |
| 3 | 每端点有最终 finding 汇总 | Memurai 键扫描 |
| 4 | finding 中 poc_status 字段非空 | JSON Schema 校验 |
| 5 | PoC 验证完成数 == finding 总数（最终轮）| Memurai 计数 |
| 6 | knowledge 缓存已合并到 knowledge.json | 文件存在性 + 字段对比 |
| 7 | 评分历史已写入 scoring-history.jsonl | 文件追加检查 |
| +1 | 端点报告数 == 端点总数（P5.4 不变量）| 文件计数 |

P5.4 不变量：等式不成立则 loop 不得终止，强制进入下一轮。
