## Phase 2 — 调用链 + 缓存 + 排序

> 关键顺序：调用链构建（AR-05）→ 链文件（AR-06）→ **方法体缓存（AR-07，缓存时机）** → sink 识别（AR-08）→ 调用链优先级排序（AR-09，按链维度）→ 鉴权类缓存（AR-10）。

- 实现锚点：`scripts/chain/chain_builder.py`（主入口）+ `scripts/chain/sqlite-extract-chain.py`
- 状态：✅

- 描述：调用链构建后、AI分析前，通过 java-method-call-extractor.jar + 源文件读取，把链上所有方法体预取到 memurai。**后续禁止直接读文件或查 codegraph 获取源码**，只能从缓存 GET。

- 实现锚点：`scripts/redis/redis-batch-prefetch.py` + `scripts/chain/method_calls_extractor.py`
- 状态：✅

### AR-08 sink 识别（动态 + 预置匹配）

- 描述：**先动态识别所有非 groupId 调用**（dynamic_sink_count），**然后用预置危险函数库匹配**（preset_sink_matches）。预置匹配用于**增加权重**（×10），预置匹配必定是 dynamic_sink_count 的子集，不单独重复计数。
  - **动态 sink**（dynamic_sink_count）：运行时通过 JAR 抽取的非 groupId 命名空间方法（覆盖所有外部依赖调用）。每个 +1 分（基础权重）。
  - **预置 sink**（preset_sink_matches）：用预置危险函数库精确匹配的（Runtime.exec、Statement.executeQuery 等 80+ 条，覆盖 SQL/RCE/LDAP/SpEL/NoSQL/XXE/反序列化/SSRF/路径穿越等 15 类）。每个 +10 分（高权重，是动态的 10 倍）。
- 工作流顺序：①JAR 抽取所有非 groupId 方法调用 → dynamic_sink_count；②预置 sink 库（约 80 条危险函数）匹配 → preset_sink_matches；③预置匹配增加权重（×10）→ 修改优先级（不单独重复计数，预置是 dynamic 的子集）。
- 输入：`chains/{endpoint}.txt` + `codegraph.db`（必选）中全部方法 FQN 列表 + 当前 `groupId` + JAR 抽取输出。
- 输出：每链 `dynamic_sink_count`（动态识别的非 groupId 调用数，基础权重×1）+ `preset_sink_matches`（匹配预置危险 sink 库的数量，高权重×10）。sink 命中明细含 `fqn`、`category`、`source`（`preset` 或 `dynamic`）。
- schema：见 `data-schema.md` 的 `chain_data.json` 段中 `queue[].dynamic_sink_count` / `queue[].preset_sink_matches` 字段。
- 实现锚点：`scripts/chain/sink_registry.py`（`PRESET_SINKS` 字典 15 类约 80 条 + `identify_dynamic_sinks()`）
- 状态：✅

### AR-09 调用链优先级排序（基于链维度，不是端点）

- 描述：**按调用链维度排序**，不是按端点排序。同一端点可能有多条链，各链独立计分。公式（区分动态 sink 与预置 sink 权重）：

  ```
  priority = base + dynamic_sink_count × 1 + preset_sink_matches × 10
  ```

  - `base`：无外部参数 `-100` / POST/PUT/DELETE/PATCH `10` / GET `0`
  - `+ dynamic_sink_count × 1`：动态识别的非 groupId 命名空间调用（外部依赖），基础权重 ×1（来自 AR-08）
  - `+ preset_sink_matches × 10`：命中预置危险 sink 库（高权重，是动态的 10 倍）（来自 AR-08）

  排序**必须**在调用链构建（AR-05）与 sink 识别（AR-08）之后，因为依赖这两个产物（dynamic_sink_count + preset_sink_matches）。
- 输入：AR-07 后的链节点 + AR-08 的 `dynamic_sink_count` / `preset_sink_matches` + 端点 HTTP 方法与参数。
- 输出：`chain_data.json`（**优先级队列，不重复存 nodes**——nodes 结构在 `chains/{endpoint}.txt`），`queue[]` 按 `priority` 降序，每链含 `chain_file` + `dynamic_sink_count` + `preset_sink_matches` + `priority` + `priority_breakdown`。
- schema：见 `data-schema.md` 的 `chain_data.json` 段中 `queue[].priority` / `queue[].priority_breakdown` 字段。
- 实现锚点：`scripts/chain/priority_calculator.py`
- 状态：✅

## Phase 3 — AI 分析（配置 → 鉴权 → 调用链）

> 分析顺序：先搞清楚"门"（配置+鉴权），再分析"内部"（调用链）。鉴权有漏洞会影响所有调用链的风险评估，故鉴权分析先于调用链。

### AR-11 环境配置导出 + AI 配置分析

- 描述：从环境（SSH 可达时）导出 nginx.conf / server.xml / JVM args / DDL / svc 配置到本地 `loop_audit/env_export/`，然后 AI 在本地分析。包括建表语句、nginx 路由、环境配置、与代码配置对比。
- 导出策略：所有环境配置**先导出到本地**，后在本地分析，不在线查询。与实际代码配置进行对比分析。SSH 不可达时离线降级（仅从代码推断）。
- 输入：SSH 环境（可选，不可达时离线降级）+ 代码中的配置文件（AR-03 config_collector 产出）。
- 输出：`config_analysis.json`（含 db_schema / nginx_routes / jvm_args / svc_configs / config_mismatches）。
- schema：见 `data-schema.md` 的 `config_analysis.json` 段。
- 实现锚点：`scripts/exposure/collectors/env_filter_collector.py` + `scripts/exposure/collectors/config_collector.py`
- 状态：⚠️（env_filter_collector 已存在但仅采集 filter，未导出 nginx/DDL/JVM 完整配置）

### AR-12 AI 认证鉴权分析（先于调用链！）

- 描述：分析 filter 链顺序（结合环境实际进程加载顺序）、JWT/OAuth/Session/注解鉴权逻辑、识别绕过可能（路径归一化差异、URL 编码差异、filter 加载顺序、黑白名单正确性）。**先于调用链分析**，因为鉴权有漏洞会影响所有调用链的风险评估。
- 输入：`auth_code` assets（AR-03 产出）+ `config_analysis.json`（AR-11 产出，含环境 filter 加载顺序）。
- 输出：`auth_analysis.json`（含 filter_chain / auth_mechanisms / bypass_risks / access_control）。
- schema：见 `data-schema.md` 的 `auth_analysis.json` 段。
- 优先级：鉴权分析先于调用链，因为鉴权有漏洞会影响所有调用链的风险评估。
- 实现锚点：`skills/auth-chain-audit/SKILL.md` + `skills/login-audit/SKILL.md`
- 状态：⏳（skills 存在但未接入 3 阶段流程）

### AR-13 AI 调用链分析（按优先级队列）

- 描述：按 `chain_data.json` 优先级队列取链，前 5 层全量加载方法体（从缓存 GET，INCR count），后续按需加载。结合 `auth_analysis.json`（鉴权有漏洞 → 相关链风险更高）。全部从 Memurai 缓存读取方法体，**不直接读文件、不查 codegraph**（已在 AR-07 通过 JAR + 源文件预取）。
- 输入：`chain_data.json` queue + `auth_analysis.json` + Memurai 缓存。
- 加载策略：
  - 前 5 层（`depth < 5`）→ 一次性 GET 完整方法体
  - 后续 → 只返回 `node_id`，AI 通过 `load_by_node_id()` 按需拉取
  - 前 5 层已确定污点消除且无业务漏洞 → 跳过后续
  - 否则继续加载，AI 自主决定
- 输出：每链一份 `chain_analysis_report.json`（原 `analysis_report.json`，重命名）。
- schema：见 `data-schema.md` 的 `chain_analysis_report.json` 段。
- 实现锚点：`scripts/analysis/method_body_loader.py` + `scripts/analysis/load_counter.py`
- 状态：✅

### AR-14 单链报告 + CVSS 4.0

- 描述：每条调用链组装一篇报告，含 verdict 三态枚举、findings（含漏洞类型、根因、入口、payload、影响）、CVSS 4.0 评分。结合 `auth_analysis`（鉴权漏洞标注）。**严禁**包含修复建议字段（硬约束）。
- 输入：调用链分析结果 + `auth_analysis.json`（鉴权漏洞标注）。
- 输出：每链一份 `chain_analysis_report.json`。
- schema：见 `data-schema.md` 的 `chain_analysis_report.json` 段。
- 实现锚点：`scripts/analysis/chain_report_generator.py`（含 `estimate_cvss_4`）
- 状态：✅

## Phase 4 — PoC + 收敛

### AR-15 PoC 三态

- 描述：PoC 验证结果分三态写回报告：`confirmed`（确认漏洞）/ `denied`（证伪）/ `inconclusive`（受环境限制无法确认）。不强制结论。
- 输入：AR-14 报告中的 findings + PoC 环境（可达 / 不可达 / 受限）。
- 输出：每链一份 `poc_result.json`。
- schema：见 `data-schema.md` 的 `poc_result.json` 段。
- 实现锚点：`scripts/audit/poc-monitor.py`（后台 daemon 轮询 Memurai 队列派发）
- 状态：✅

### AR-16 收敛判定 4-AND

- 描述：四项指标同时达标才允许终止 loop：平均分 ≥ 85、标准差 < 3、数据对账通过 ≥ 10 次、端点覆盖率 ≥ 0.95。
- 输入：当前轮次的 4 项指标（`avg` / `std` / `reconcile` / `coverage`）。
- 输出：`convergence.json`，4 项同时达标返回 `True`，否则 `False` 触发新一轮。
- schema：收敛结果简单 JSON，无独立 schema 段（字段即 4 指标 + 布尔）。
- 实现锚点：`scripts/audit/self_evolution.py`（`calculate_convergence()`）
- 状态：✅

### AR-17 知识沉淀

- 描述：把本轮发现的自定义注解、已知消毒器、动态路由模式、finding 模式写入 `knowledge.json` 与 `{groupId}:knowledge:*` Memurai 键，下一轮自动加载。
- 输入：本轮 findings + 新发现的消毒器与注解。
- 输出：`{loop_audit_dir}/knowledge.json` + Memurai `{groupId}:knowledge:*` 键。下一轮经 `merge_knowledge_from_memurai()` 合并进上下文。
- schema：见 `data-schema.md` 的 `knowledge.json` 段。
- 实现锚点：`scripts/audit/self_evolution.py`（`merge_knowledge_from_memurai()`）
- 状态：✅
