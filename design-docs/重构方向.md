## P0：阻塞性问题与已知 bug

P0 项处理已经影响功能正确性的缺陷。修复前不应启动新特性工作，否则知识沉淀、测试加载、链路查询都会被这些问题污染。四项均不互相阻塞，建议在下一个迭代周期内全部完成。

### P0-1 方法体加载次数追踪未接入主管线

- 现状数据：`scripts/analysis/load_counter.py` 已实现 load_ratio 计算，但 `scripts/audit/cross-agent-50r.py`（376 行）未调用它，导致 load_ratio 指标无法测量。
- 目标数据：每轮结束产出 `round_metrics.json` 含 `load_ratio` 字段，且首轮值 < 0.3。
- 工作步骤：1) cross-agent-50r.py 调 self_evolution 收尾时加 `load_counter.get_metric()`；2) round_metrics.json 写出 load_ratio；3) 跑一轮验证字段存在且 < 0.3。
- 预期收益：可量化"AI 看了多少方法体"，识别低效轮次。
- 风险：低。改动局部，仅追加一次调用。
- 涉及文件：`scripts/audit/cross-agent-50r.py`、`scripts/analysis/load_counter.py`、`scripts/audit/self_evolution.py`

### P0-2 调用链 verdict 三态未标准化

- 现状数据：`analysis_report.json` 的 `verdict` 字段无枚举约束（chain_report_generator.py 已有该字段但未校验取值），导致 vuln_chains、safe_chains、unknown_chains 无法准确统计。
- 目标数据：verdict 强制枚举 `{"vuln", "safe", "unknown"}`，非法值在生成阶段即被拒绝。
- 工作步骤：1) chain_report_generator.py 加枚举校验；2) 非法 verdict 抛错而非静默写入；3) 统计脚本按三态聚合，验证三个集合之和等于总链数。
- 预期收益：评价指标基线表里 6 个指标中的准确率、召回率可正确计算。
- 风险：低。
- 涉及文件：`scripts/analysis/chain_report_generator.py`

### P0-3 conftest.py 中文路径残留导致 import 失败

- 现状数据：`scripts/tests/conftest.py`（第 13 至 16 行）与 `test_scripts/conftest.py`（第 7 至 10 行）共 8 处 `sys.path.insert` 指向字符串 `"脚本"`，实际目录名为英文 `"scripts"`。测试套件 import 直接失败。
- 目标数据：8 处引用全部改为 `"scripts"`，pytest 收集阶段无 ImportError。
- 工作步骤：1) grep 全仓确认无其他 `"脚本"` 字面量；2) 替换两个 conftest.py 的 8 处引用；3) 跑 `pytest scripts/tests` 验证收集通过。
- 预期收益：测试套件可用，覆盖率统计（P2-1）的前提条件。
- 风险：低。纯路径替换。
- 涉及文件：`scripts/tests/conftest.py`、`test_scripts/conftest.py`

### P0-4 merge_knowledge 新 knowledge 类型被静默丢弃

- 现状数据：`self_evolution.py`（646 行）第 415 行 `merge_knowledge_from_memurai` 用 `suffix = key.split(":")[-1]` 取类别，再 `if suffix in existing` 判断。`existing` 的 key 集合由预置结构决定，新增 knowledge 类型若不在预置 key 内会被静默跳过。
- 目标数据：任意 `{groupId}:knowledge:*` 子类型都能合并，不依赖预置 key 白名单。
- 工作步骤：1) 为现有合并行为写回归测试锁定；2) 改判断为"suffix 不在 existing 则自动初始化新分类"或前缀匹配 `key.startswith(f"{groupId}:knowledge:")`；3) 新增一个未注册 suffix 验证可合并。
- 预期收益：项目特有知识不丢失，沉淀完整性达标。
- 风险：低。已有覆盖，改动局部。
- 涉及文件：`scripts/audit/self_evolution.py`

## P1：架构改进与 RFC-0001 集成

P1 项推动代码向 RFC-0001 的 SOLID 架构收敛，并清理 skills/ 目录的结构性噪声。每项都需要端到端回归测试，避免审计结果漂移。

### P1-1 cross-agent-50r.py 接入新 exposure 管线

- 现状数据：daemon（cross-agent-50r.py，376 行）仍调用旧 `scripts/ast/attack_surface_scanner.py`（1469 行单体）。RFC-0001 已落地 `scripts/exposure/` 共 8 个 collector（auth_code、codegraph、config、db_schema、env_filter、route、sensitive_info、waf）加 cli.py（205 行），但 daemon 未接入。新旧管线并存。
- 目标数据：daemon Phase 1 改为调 `python -m scripts.exposure.cli collect`，输出 `exposure/*.json`，旧扫描器降级为 fallback。
- 工作步骤：1) 加 feature flag（preset 字段或环境变量）切换新旧管线；2) 集成测试对比同一 preset 下新旧输出差异；3) 差异可接受且收敛无回归后默认启用新管线。
- 预期收益：攻击面发现逻辑统一到单一可维护入口，单文件行数从 1469 降到 ≤250/模块。
- 风险：高。daemon 是核心入口，输出差异可能导致收敛指标偏移，需多轮回归。
- 涉及文件：`scripts/audit/cross-agent-50r.py`、`scripts/exposure/cli.py`、`scripts/ast/attack_surface_scanner.py`

### P1-2 消除 endpoint-supervisor 悬空引用

- 现状数据：`skills/endpoint-supervisor/SKILL.md` 第 55 行与第 146 行引用 `skills/call-chain-audit-thinking/SKILL.md`，该路径不存在。agent 加载时会跳过或报错。
- 目标数据：悬空引用计数降为 0。
- 工作步骤：1) 确认 call-chain-audit-thinking 的能力当前如何实现（是否已合并进 endpoint-supervisor）；2) 决策：合并到 endpoint-supervisor（删引用）或创建独立 skill（补实现）；3) 修改 endpoint-supervisor/SKILL.md 的 2 处引用。
- 预期收益：消除 agent 加载歧义，调用链审计能力路径明确。
- 风险：低。文档级修改。
- 涉及文件：`skills/endpoint-supervisor/SKILL.md`

### P1-3 迁移 arthas-doc 离线文档

- 现状数据：`skills/arthas-audit/arthas-doc/` 含 572 个 Arthas 官方文档拷贝文件，skills/ 总文件数 600，占比 95.3%。内容只是离线文档，不被代码逻辑使用。
- 目标数据：移到 `tools/arthas-doc/`，skills/ 文件数从 600 降到约 28，瘦身约 95%。
- 工作步骤：1) grep 确认 `arthas_exec.py` 不依赖这些静态文件路径；2) 移动整个 arthas-doc/ 目录到 tools/；3) 修改 SKILL.md 中对文档路径的引用，或改为运行时按需 fetch。
- 预期收益：skills 目录瘦身 95%，降低 skill 扫描成本与认知噪声。
- 风险：中。若 arthas_exec 实际有路径依赖会断链，需先验证。
- 涉及文件：`skills/arthas-audit/arthas-doc/**`、`skills/arthas-audit/SKILL.md`

### P1-4 漏洞知识从 prompt 迁移到 skill

- 现状数据：部分 `prompts/*.md` 内联漏洞识别知识（SQLi、XSS、SSRF 等判据），既浪费 token 又与 skills/*/SKILL.md 重复维护。
- 目标数据：prompt 仅含调度逻辑与角色边界，漏洞识别知识全部归集到对应 skills/*/SKILL.md。
- 工作步骤：1) grep prompts/ 中的漏洞判据段落；2) 逐类迁移到对应 skill（injection-audit、auth-chain-audit 等）；3) prompt 改为引用 skill 名称，不再内联判据。
- 预期收益：prompt 简洁，token 消耗下降，漏洞知识集中维护。
- 风险：中。迁移后需验证 subagent 仍能正确加载判据，避免漏检。
- 涉及文件：`prompts/*.md`、`skills/*/SKILL.md`

## P2：质量提升

P2 项不阻塞功能，但提升可维护性与文档可信度。可在新版本迭代中渐进推进。建议 P2-1 与 P0-3 联动（conftest 修好后才能跑覆盖率统计）。

### P2-1 补齐核心模块测试覆盖率到 80% 以上

- 现状数据：`scripts/exposure/` collectors 有配套测试（8 个 collector 对应 8 个 test 文件），但 `memurai_client.py`（482 行）覆盖率 0%，`cross-agent-50r.py`（376 行）覆盖率 0%。
- 目标数据：所有核心模块覆盖率 ≥ 80%。
- 工作步骤：1) 先修复 P0-3（conftest 路径），让 pytest 能收集；2) 为 memurai_client mock subprocess 调用，覆盖正常路径、连接失败、超时、批量原子性；3) 为 cross-agent-50r 拆出可测函数，覆盖轮次调度逻辑；4) 跑覆盖率报告确认 ≥ 80%。
- 预期收益：缓存层与 daemon 改动有回归保护，降低 P0 类 bug 再发概率。
- 风险：低。
- 涉及文件：`scripts/redis/memurai_client.py`、`scripts/audit/cross-agent-50r.py`、对应 tests/

### P2-2 为主 SKILL.md 瘦身到 50 行以内

- 现状数据：主 `skills/java-whitebox-loop/SKILL.md` 126 行，是原子需求 #14 目标（≤50 行）的 2.5 倍。
- 目标数据：≤ 50 行，仅保留调度骨架，详细规则外移到 rules/。
- 工作步骤：1) 提取用户入口契约到 `rules/entry-contract.md`；2) 提取目标对齐内容到 `rules/goals.md`；3) 主文件只保留阶段编号、子 skill 路由、收敛判据指针。
- 预期收益：满足原子需求 #14，降低单文件认知负载。
- 风险：中。拆分后需确认 agent 仍能正确加载全部规则，避免规则丢失。
- 涉及文件：`skills/java-whitebox-loop/SKILL.md`、`skills/java-whitebox-loop/rules/entry-contract.md`（新建）、`skills/java-whitebox-loop/rules/goals.md`（新建）

### P2-3 重写 doc/TDD.md

- 现状数据：`doc/TDD.md` 已归档到 `doc/archive/`，原版引用 6 个不存在的脚本与不存在的 test_scripts/、fixtures/ 目录，完全失配现状。
- 目标数据：基于现存 19 个 `scripts/*/tests/` 模块重建测试矩阵。
- 工作步骤：1) glob 现存所有 `scripts/**/tests/` 与 conftest.py；2) 重写测试矩阵，列出现存模块、覆盖范围、运行命令；3) 加 conftest 修复指引（联动 P0-3）。
- 预期收益：TDD 文档可信，新成员能据此跑通测试。
- 风险：低。
- 涉及文件：`doc/TDD.md`

### P2-4 简化评价指标输出

- 现状数据：`self_evolution.py`（646 行）输出多个分散指标文件，下游消费方需自行聚合，存在冗余。
- 目标数据：每轮仅输出一个 `round_metrics.json`，含 6 个评价指标（load_ratio、vuln_chains 准确率、召回率、方差、对账通过数、覆盖率）。
- 工作步骤：1) 确认 metric_simplifier 输出格式（若存在）；2) self_evolution 调用它统一输出；3) 删除冗余的分散指标文件。
- 预期收益：下游统计脚本简化，指标来源单一可信。
- 风险：低。
- 涉及文件：`scripts/audit/self_evolution.py`

## P3：长期演进

P3 项面向架构长期演进，优先级最低，但为未来版本铺路。

### P3-1 实现 scripts/generated/ 自生成脚本机制

- 现状数据：scripts/generated/ 不存在，所有脚本硬编码在仓库，无法按项目定制（原子需求 #16）。
- 目标数据：Boss agent 运行时生成项目专用脚本，带 groupId 命名空间隔离，生成产物不入库。
- 工作步骤：1) 设计 `scripts/generated/{groupId}/` 目录结构与命名约定；2) 在生成器中加 project_id 命名空间，避免跨项目污染；3) 加 .gitignore 规则。
- 预期收益：满足原子需求 #16，支持项目级定制而不污染主干。
- 风险：中。生成脚本的生命周期管理（清理、版本）需要配套设计。
- 涉及文件：`scripts/generated/`（新建）、`.gitignore`

### P3-2 验证 SSH 配置检查的远程执行路径

- 现状数据：`scripts/exposure/collectors/env_filter_collector.py`（144 行）已存在，但未验证是否真正通过 SSH 远程执行，可能只是本地模拟（原子需求 #8）。
- 目标数据：通过 ssh-skill 做真实远程检查，filter 链从目标环境拉取。
- 工作步骤：1) 在 WebGoat 容器中部署测试环境，暴露 SSH；2) 验证 filter 链能否通过 SSH 真实拉取；3) 加集成测试覆盖远程路径。
- 预期收益：满足原子需求 #8，filter 审计能力真实可用。
- 风险：中。SSH 集成涉及凭据管理与超时，需配套错误恢复。
- 涉及文件：`scripts/exposure/collectors/env_filter_collector.py`、`skills/ssh-skill/`

### P3-3 工具评估文档持续维护

## 实施建议

- **P0 优先，不互相阻塞**：4 项改动局部，约 1 天可全部完成。P0-3（conftest 路径）改动最小，可先做解锁 P2-1 的覆盖率统计。
- **P1 需端到端回归**：4 项都涉及架构收敛，每项完成后必须跑一次完整 audit preset 验证收敛指标无回归。P1-1（exposure 管线接入）风险最高，建议放最后。
- **P2/P3 渐进推进**：可分配到不同版本迭代，无需集中批次。P2-1 与 P0-3 联动收益最大，建议同期做。
- **依赖关系**：P0-3 修复后 P2-1 的覆盖率统计才有意义；P0-1 修复后 P2-4 的 round_metrics.json 才能含 load_ratio；P1-3 完成后 P2-2 的 rules/ 拆分更顺。建议按依赖顺序排期。
- **数据复核**：本文档所有行数、文件数均经 2026-06-19 实测。后续实施前如代码已变动，需重新 grep 复核，避免数据漂移。
- **不实施承诺**：本文档仅规划，不含实施。
