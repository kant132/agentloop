本文件为项目的根本
本项目的根本目标
1、代码审计输出漏洞准确已被验证，是/非漏洞
2、外部接口无遗漏
3、接口调用链分析无遗漏
4、运行高效，消耗token少
5、工具自进化，越用越智能，越用越快。

准则
所有目标都是为了发现漏洞，其他任何对目标没有帮助的内容，都需要删除。
每轮agentloop 清空上一轮的缓存groupId开头的都清除了。

难点：
如何准确表达需求，拆分原子需求
如何让agent准确无误执行本工具的指令：执行路径，执行过程，执行结果，执行效率，无幻觉
如何做工程优化：剪枝、Memurai缓存
如何工具自进化：每次代码审计结束主agent进行反思，输出工具改进建议；沉淀项目特有知识，特殊经验等，指导下次审计
工具迭代如何保证逻辑的一致性，如何保证工具迭代能力不会退化，不会过拟合某个项目

思维角度：
大版本改动前读取本文档，并启动三方评审skill


输出模板约束

所有产出写入目标项目的 `loop_audit/`（相对项目根目录）。

```
loop_audit/
 ├── project-context.json      ← Phase A：技术栈、依赖、端点总表
 ├── security-context.json     ← Phase B：Filter链、威胁模型、配置风险
 ├── findings/{chainId}.json   ← 机器可读 finding（评分后落盘）
 ├── routes/
 │    ├── 高风险端点/*.md      ← 按端点的审计报告
 │    ├── 中低险端点/*.md
 │    └── poc/*.md             ← PoC 验证报告
 ├── reports/
 │    ├── summary.md           ← 1 页执行摘要（给人类看）
 │    ├── api-audit/*.md       ← 按 API 方法展开
 │    └── vuln-report/*.md     ← 按 finding 展开（含 trust_type + exploitability）
 ├── diag/                     ← 过程遥测（机器用，不进报告）
 │    ├── findings.jsonl
 │    ├── scoring-history.jsonl
 │    ├── pruning-log.jsonl
 │    └── false-positive-samples.jsonl
 ├── needs_human/              ← 不可达/需人工确认的端点
 └── knowledge.json            ← 跨轮次知识沉淀
```

模板源文件在 `agentloop/loop_audit/_template/`。

文件命名：
- 端点报告：`{severity}_{fqn}_{method}_{sigHash}.md`（Windows 兼容，点号→`__`）
- PoC：`{验证状态}_{问题等级}_{fqn.端点method-sink点-roundNNN}.md`
- 验证状态枚举：是问题 / 非问题 / 暂时无法确认

不变量：端点报告总数 == `project-context.json` 中 endpoints 总数（不等则 loop 不可终止）。



# 原子需求拆解

每条原子需求是系统必须具备的不可再拆能力，去掉任何一条，系统都有真实缺陷。

流程：
1. 项目一次阅读理解。agent 进入项目后，一次读完文档、技术栈、依赖、端点清单，不跨多个 phase 反复切换。现状：分 P1/P2/P4 三个 phase，重复扫描。 
-- ok，减少工作量，只进行外部端口扫描和filter等重要文件发现，不做威胁分析了，阅读文档等耗时工作。后面人工单独做。需要缓存。当前的实现是否是一次性查询到一个source点的20层调用链（所有）。
这一步需要优先确定，项目存在哪些路由方式。然后自己选择已经的脚本，还是写脚本，还是ai智能分析，需要有一个策略。需要预置一部分框架的路由方式。知道吗，也是框架skill，使用spring，就加载spring的，使用了soap就加载他的，执行路由查询和重要的影响安全的文件识别。

2. 安全上下文在漏洞分析前完整就绪。agent 进入调用链分析时，Filter 链、消毒器清单、威胁模型、配置风险已全部加载到上下文。现状：分散在 P2/P3，Phase 5 还要反复回查。
-- 需要合并，缓存
3. 调用链审计能发现可利用漏洞。agent 拿到一条调用链后，知道该思考什么、关注什么、哪些是陷阱，能产出有真实代码证据的漏洞 finding。现状：5 个 subagent 各跑各维度，互不交叉，漏洞发现依赖碰运气。 
-- 已经抽象为skill: skills/call-chain-audit-thinking/。，专门引导ai 思考，同时给ai足够的自由度。 同时，漏洞发现， poc验证只有在漏洞报告标记finished之后才能启动subagent执行。 专门设置2个子agent进行poc验证。 注意所有状态信息需要保存在缓存里，可以写一个后台python，while 从缓存里取到 finished的调用链，然后调用poc agent进行验证，后把验证结果给主agent。

4. 审计结束有结构化自检。每轮结束时，agent 按 if-then-else 清单自检，输出可验证的 JSON 报告。现状：自检要求从三个哲学视角反思，无法验证。  
-- ok 
5. 假阳率有量化度量。每轮抽样标注，知道假阳率是多少、趋势是升还是降。现状：完全不知道。
-- ok
判定：
6. 每个漏洞同时有技术分类和信任分类。技术分类用于工具匹配（SQLi/XSS），信任分类用于开发者理解（不可信输入/缺鉴权/缺业务规则）。现状：只有技术分类。 
-- 删除
7. 每个漏洞有攻击可行性评估。标注是否需要认证、是否在 WAF 后面、攻击复杂度。现状：漏洞报告显示一堆漏洞不知道哪个真的能打。 
-- 是的，需要标注调用链上的每个方法，的业务意义，分支逻辑，参数传递影响（这个可以缓存，这次分析了，下次可以直接复用）
8. 配置风险能被发现。从代码中 visible 的配置（csrf.disable、默认密码、session 策略）主动检查。现状：不查。  
-- 需要ssh 去环境上检查。
9. 硬编码凭证能被发现。password/secret/apiKey 等硬编码模式主动扫描。现状：不查。  
-- 不是代码审计重点，重点是发现可被利用的，攻击类的漏洞。非合规漏洞，当然，如果密码可以被泄露，就算，因为影响cia。

沉淀：
10. 项目知识跨轮次持久化。自定义注解、已知消毒器、动态路由模式、、历史 finding 模式，下一轮自动加载，不再从零开始。现状：每轮重新学。
-- ok
11. 评分历史可追溯。每轮评分持久化，能计算方差和趋势，而不是凭记忆。现状：算不了。
-- ok
12. 收敛有客观标准。连续 N 轮方差<5 且均分>85 且对账全过。现状：只有"连续 3 轮>85"，方差无法计算。
-- ok
13. 有效优化不丢失。被验证有效的优化建议持久化到经验库，不随轮次消失。现状：每轮重新想。
-- ok

密度：
14. 主 SKILL 一次能读完。压缩到 50 行以内，只说 agent 不知道的。现状：139 行，包含大量 AI 已知的通用知识。
-- ok
15. rules 文件数量可控。agent 启动时读 3 个文件而不是 7 个。现状：7 个 files，交叉引用复杂。
-- ok
工具链：
16. Phase A 有确定性脚本。codegraph 初始化、技术栈识别、端点枚举不用 LLM 做。现状：全靠 LLM。
-- 工具初始状态是这样，后续可以预置知识和脚本，主要是工具在使用过程中自己生成脚本和知识，项目特有的知识需明确标注，避免互相干扰。
17. 工具有降级路径。codegraph 不可用时降级到 ast-grep，Memurai miss 时降级读文件。现状：降级逻辑散落在各处，没有矩阵。
-- codegraph ast-grep Memurai不能使用，直接推出。
18. 报告只有 3 类。执行摘要、API 审计、漏洞报告，每个 finding 一个文件。现状：12 个模板，agent 选择困难。
-- 每个步骤明确指明，需要用什么模板。
