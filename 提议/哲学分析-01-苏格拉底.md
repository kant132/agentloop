# 苏格拉底：诘问式分析

> 方法：不断追问「为什么」，直到触及不可再分的基本事实。每个回答都可能被下一个问题推翻。

---

## 第一层诘问：这个项目要做什么？

**问**：AgentLoop 项目要做什么？

**答**：自动化 Java 代码白盒安全审计。

**问**：什么是「白盒安全审计」？

**答**：在能看到源代码的前提下，发现代码中的安全漏洞。

**问**：什么是「安全漏洞」？

**答**：代码中违反安全属性的缺陷——机密性（数据不泄露）、完整性（数据不被篡改）、可用性（服务不中断）。

**问**：那「发现」漏洞意味着什么？

**答**：找到一条从外部输入（source）到危险操作（sink）的路径，且路径上没有有效的消毒。

**问**：所以审计的本质是什么？

**答**：枚举所有 source → sink 的路径，判断每条路径是否安全。

---

## 第二层诘问：为什么要自动化？

**问**：为什么要让 AI 做这件事，而不是人？

**答**：减少人类工作流，提升效率。

**问**：效率提升多少才算成功？

**答**：用户没说。但原始需求说「减少人类工作流」。

**问**：「减少」是什么意思？是减少到 0，还是减少 50%？

**答**：不知道。这是模糊的需求。

**问**：如果人类工作流减少到 0，AI 完全自主审计，那还需要人类吗？

**答**：需要。人类需要定义 Skill、验收标准、处理 AI 无法判断的情况。

**问**：所以「减少人类工作流」的真正含义是什么？

**答**：让人类只做「不可替代」的工作——定义规则、验收结果、处理边缘情况。AI 做「可替代」的工作——执行规则、生成报告、验证漏洞。

---

## 第三层诘问：什么是「不可替代」的工作？

**问**：人类在审计中做什么不可替代的工作？

**答**：
1. 定义「什么是漏洞」——业务规则、安全标准
2. 判断「这个发现是不是真的漏洞」——AI 可能误报
3. 决定「这个漏洞要不要修」——优先级、成本收益
4. 理解「这个系统在做什么」——业务上下文

**问**：这些工作中，哪些可以形式化为 Skill？

**答**：
- 可以形式化：部分漏洞定义（SQLi、XSS 有明确模式）
- 难以形式化：业务规则（每个项目不同）、判断真伪（需要经验）、优先级（需要上下文）

**问**：所以 Skill 的极限在哪里？

**答**：Skill 可以捕获「通用模式」（SQLi 的判定规则），但不能捕获「项目特定知识」（这个项目的业务规则）。

**问**：那项目特定知识怎么给 AI？

**答**：通过文档、通过项目记忆、通过 Phase 1 的业务建模。

---

## 第四层诘问：当前实现解决了什么？没解决什么？

**问**：当前 6 阶段流程解决了什么？

**答**：
- Phase 1：识别环境和业务上下文
- Phase 2：威胁建模，确定优先级
- Phase 3：分析 Filter/拦截器，识别全局消毒
- Phase 4：枚举外部端点
- Phase 5：分析调用链，发现漏洞
- Phase 6：汇总、反思、优化

**问**：这个流程有什么问题？

**答**：
1. **过度工程化**：6 阶段、7 篇必读、4 种 FWD 模式，LLM 需要读太多文档
2. **信息冗余**：Skill 文档太长（120+ 行），引用文件太多（15+）
3. **缺少持久化**：评分历史、优化建议、项目知识没有持久化机制
4. **工具协调不清晰**：列出了工具，但没说清楚怎么协调

**问**：这些问题会导致什么后果？

**答**：
1. LLM 上下文爆炸——读太多文档，忘记核心任务
2. 执行效率低——重复读取、重复分析
3. 无法收敛——没有持久化，无法判断「连续 3 轮 > 85 分」
4. 工具混用——不知道何时用 codegraph，何时用 ast-grep

## 第五层诘问：原子需求是什么？

**问**：如果把所有实现细节剥掉，原子需求是什么？

**答**：

**原子需求 1：枚举 source → sink 路径**
- 输入：项目源代码
- 输出：所有从外部输入到危险操作的路径
- 约束：路径数量可能很大（1000+），需要剪枝

**原子需求 2：判断路径安全性**
- 输入：一条 source → sink 路径
- 输出：安全 / 不安全 / 不确定
- 约束：需要考虑路径上的消毒器、业务规则、框架隐式行为

**原子需求 3：验证漏洞**
- 输入：一个「不安全」的路径
- 输出：PoC 验证通过 / 验证失败 / 环境不可达
- 约束：需要真实环境，可能不可达

**原子需求 4：生成报告**
- 输入：所有发现
- 输出：人类可读的报告
- 约束：结果先行、数据对账、人类可审计

**原子需求 5：知识沉淀**
- 输入：本轮审计的经验
- 输出：可复用的 Skill / Pattern
- 约束：跨项目通用 vs 项目特定

---

## 第六层诘问：当前实现偏离原子需求多远？

**问**：当前实现覆盖了多少原子需求？

**答**：
- 原子需求 1（枚举路径）：✅ 覆盖（codegraph + ast-grep）
- 原子需求 2（判断安全性）：⚠️ 部分覆盖（有规则，但规则太复杂）
- 原子需求 3（验证漏洞）：⚠️ 部分覆盖（有 PoC 流程，但环境依赖大）
- 原子需求 4（生成报告）：✅ 覆盖（有报告模板）
- 原子需求 5（知识沉淀）：❌ 未覆盖（没有持久化机制）

**问**：最大的偏离是什么？

**答**：

**偏离 1：复杂度过高**
- 原子需求 2 只需要「判断路径安全性」
- 当前实现：4 种 FWD 模式、7 篇必读、15+ 引用文件
- 偏离度：高

**偏离 2：缺少反馈循环**
- 原子需求 5 需要「知识沉淀」
- 当前实现：没有持久化，每轮都是「从零开始」
- 偏离度：高

**偏离 3：工具协调不清晰**
- 原子需求 1 需要「枚举路径」
- 当前实现：列出了 codegraph、ast-grep、LSP，但没说清楚怎么协调
- 偏离度：中

## 苏格拉底式结论

**最终诘问**：这个项目能成功吗？

**答**：取决于如何定义「成功」。

- 如果成功 = 「完全自主审计，人类零干预」→ 不能成功（先验限制）
- 如果成功 = 「减少人类工作流 50%」→ 可能成功（需要简化实现）
- 如果成功 = 「形成可复用的审计知识」→ 可以成功（需要持久化机制）

**苏格拉底式建议**：

1. **承认不完美**：AI 审计永远不完美，接受它
2. **聚焦原子需求**：简化实现，聚焦 5 个原子需求
3. **建立反馈循环**：持久化知识，让每轮审计都比上一轮更好
4. **人类在环**：保留人类判断，不要试图完全自动化
