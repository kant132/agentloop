# 必读 05：不写修复硬约束

> **目的**：本 loop 业务目标 = **只深度发现所有致命/严重问题 + 找出漏洞点 + PoC 验证**。**绝不修，绝不写修复建议**。

## 一、明确边界

| 在 scope | 不在 scope |
|----------|-----------|
| 漏洞点定位（file:line） | 修复方案 |
| 调用链追溯 | 修复代码示例 |
| PoC payload | 加固建议 |
| 业务影响描述 | "建议加 @PreAuthorize" |
| 严重性评级 | 修复优先级排序 |
| 触发条件说明 | 临时缓解措施 |

## 二、为什么不能写修复

1. **诱导越界**：写修复 → 写更多加固 → 跑题
2. **消耗 token**：修复示例通常比漏洞描述长 3-5 倍
3. **污染评分**：修复质量混入漏洞质量评分，分散注意力
4. **角色错位**：agent 不是修复者，修复由开发团队做

## 三、subagent 输出 schema 禁止字段

finding JSON 中**禁止**包含以下字段：

```json
{
  ❌ "remediation": "...",
  ❌ "fix_suggestion": "...",
  ❌ "secure_alternative": "...",
  ❌ "how_to_fix": "...",
  ❌ "patch": "..."
}
```

**允许**的字段：
- `location`（file:line）
- `evidence_chain`（调用链节点）
- `poc_payload`（验证用，不是修复用）
- `business_impact`（影响描述）
- `prerequisites`（利用前置条件）

## 四、prompt 强制项

```markdown
## 严格禁止
- 不输出任何修复建议
- 不输出修复方向（如"应使用 PreparedStatement"）
- 不输出修复代码示例
- 不输出"建议"性内容
- 即便漏洞修复非常简单，也只记 location，不记 fix
```

## 五、检测

- 评分 subagent 发现 `remediation` 字段 → 直接 0 分
- 反思 subagent 发现"应该"、"建议"、"考虑改用"等修复性词汇 → 扣 10 分

## 六、例外

如未来 loop 升级包含"修复模式"，必须**新开一个 subagent**（`FIX-X`），不与 `FWD-X` 混用。
