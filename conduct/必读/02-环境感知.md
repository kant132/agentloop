# 必读 02：环境感知

> **目的**：PoC 验证不是无脑执行，而是受环境状态门控。

## 一、环境状态三态

| 状态 | 含义 | PoC 策略 |
|------|------|----------|
| **可达** | 业务部署环境可访问（前端 URL 通、SSH 通） | 完整 PoC |
| **不可达** | 环境完全无法连接 | 跳过 PoC，标 `poc=skipped_unreachable` |
| **受限** | 部分可达（如只有 SSH 没前端、只有测试环境） | 降级 PoC，标 `poc=degraded` |

## 二、状态判定时机

### 2.1 Phase 1（环境识别）
- SSH 登录测试 → SSH 可达？
- HTTP HEAD 测试 → 前端可达？
- 网络拓扑分析 → 内部网络可达？

### 2.2 状态写入 Memurai
```
audit:{groupId}:commit:{commitHash}:env:reachability
  → {
      "ssh": "reachable" | "unreachable" | "degraded",
      "http": "reachable" | "unreachable" | "degraded",
      "topology": "...",
      "last_check": "2026-06-12T...",
      "checker": "phase1-orchestrator"
    }
```

> 写入走 `memurai-cli SET key value EX 3600`（TTL 1h）。

### 2.3 FWD / PoC subagent 读取
- 启动前必读 `:env:reachability`（`memurai-cli GET`）
- 不可达 → 跳过 PoC，finding 标记 `poc_status=skipped`
- 受限 → 仅做可行部分的 PoC

## 三、SSH 的双重角色

**不要把 SSH skill 当作"PoC 时连接"的工具**。SSH skill 有两重用途：

### 3.1 Phase 1 拓扑发现（必做）
- 登录后看路由表 / iptables / nginx 配置
- 生成 `.drawio` 路由图
- 报告**端口 → 路径 → 上游**的映射

### 3.2 PoC 验证（按需）
- 复用 Phase 1 已建立的 SSH 连接
- 不要重新建立连接
- 执行 payload → 观察日志

## 四、降级 PoC 的具体做法

| 完整 PoC | 降级 PoC | 不可达 PoC |
|----------|----------|-----------|
| 浏览器 + SSH + 数据库连接 | 仅 SSH 验证服务端日志 | 仅代码静态论证 |
| 真实 payload | 模拟 payload（不触发破坏） | 无 |
| 影响面验证 | 仅验证可达性 | 仅做理论分析 |

## 五、环境信息修正

环境信息 = **业务部署环境**（不是代码运行环境）：
- ✅ 前端 URL、后端 SSH、网络拓扑、上下游系统
- ❌ JVM 版本、容器镜像、CPU 架构

读取 `doc/` 目录下所有文档（业务需求、架构手册、部署手册、用户手册、MD）→ 提取业务域 + 攻击面。

## 六、违反的代价

- 在不可达环境跑 PoC = 浪费 30+ 分钟
- 把代码运行环境当作业务环境 = 整个 PoC 框架错位
- 不做拓扑发现 = 不知道哪些端点真正对外 = 漏报高危端点
