# 必读 03：工具选择边界

> **目的**：明确 5 类工具的适用场景，避免混用降低效率。

## 一、5 类工具分工

| 任务 | 工具 | 备注 |
|------|------|------|
| **配置文件扫描** | `grep` | web.xml / yml / properties |
| **类/方法/调用关系查询** | `codegraph SQLite` | 最多 20 LEFT JOIN |
| **简单代码模式匹配** | `ast-grep` | 危险函数调用（SQL/RCE/...） |
| **调用链批量提取** | `codegraph SQLite CTE RECURSIVE` | 带环检测 + 深度控制 |
| **方法体读取** | codegraph → Memurai 缓存（走 memurai-cli） | subagent 全程读 Memurai |
| **业务方法反向被调查询** | `codegraph SQLite` | 多端点共享一业务方法 |
| **统计 / 报表** | `Python 脚本` | chain-stats / coverage-audit |

## 二、决策树

```
要查什么？
│
├─ 配置文件里的值？  ──→ grep
│
├─ 类/方法的某种特征？  ──→ codegraph SQL（最多 20 LEFT JOIN）
│
├─ 危险函数调用模式？  ──→ ast-grep
│
├─ 从 A 到 B 的所有路径？  ──→ codegraph CTE RECURSIVE
│
├─ 读取方法体？  ──→ 先查 Memurai，未命中再 codegraph
│
└─ 数据统计 / 对账？  ──→ Python 脚本
```

## 三、错误使用

❌ 用 ast-grep 扫整个项目找"被 Controller 调用的 Service"
- 应该用 codegraph SQL 一句 JOIN 搞定

❌ 用 grep 找方法体里的 `Runtime.exec(...)`
- 应该用 ast-grep 匹配危险模式

❌ 直接 `Read` 整文件读方法体
- 应该 codegraph → Memurai

❌ 用 codegraph 配置文件路径查 git 历史
- 应该用 git 命令

## 四、性能数量级

| 操作 | 耗时 | Token |
|------|------|-------|
| `Read` 整文件（1KB） | ~50ms | 全文加载 |
| codegraph SQL 单查询 | ~10-100ms | 仅结果 |
| Memurai hit（memurai-cli GET） | ~30ms（含子进程） | 仅 value |
| Memurai MSET 100 keys | ~50ms 一次 | 批量 |
| ast-grep 单文件 | ~20-200ms | 匹配行 |
| codegraph CTE RECURSIVE（深度 20） | ~100-500ms | 链节点 |

**结论**：能用 codegraph SQL 的，**不要**用 ast-grep 扫全文件；能用 Memurai hit 的，**不要**再调 codegraph。

## 五、强制规则

- subagent 启动前已预取 chain 方法到 Memurai → subagent **不直接调** codegraph
- 配置文件查询用 grep，**不**用 codegraph（codegraph 不解析 yml）
- 复杂关系（> 5 个表 JOIN）必须用 codegraph SQL，**不**用 ast-grep 多次扫描
