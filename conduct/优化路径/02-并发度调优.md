# 优化路径 02：并发度调优

> 并发不是越多越好，受 codegraph / Memurai（subprocess 进程数）/ LLM 限流约束。

## 一、并发层级

| 层级 | 单位 | 默认 | 上限 |
|------|------|------|------|
| **FWD 模式** | 每端点 | 4 | 4（A+B+C+D） |
| **端点并行** | 全局 | 3 | 10 |
| **subagent 失败重试** | 每 subagent | 2 | 3 |

## 二、约束来源

### 2.1 codegraph
- SQLite 单写锁 → 读并发高，写并发低
- 单查询 < 100ms 视为正常
- 10+ 并发查询 → 排队等待

### 2.2 Memurai（走 memurai-cli.exe）
- 每次调用 = 1 个子进程（~30ms 启动）
- 一次 `MSET` 可传 ~1000 keys（受命令行长度限制）
- **Memurai 自身的 QPS 不是瓶颈**，瓶颈是并发子进程数
- Windows 上同时跑 50+ memurai-cli 进程会触发进程数警告，控制在 ≤ 30 并发

### 2.3 LLM API
- 限流（按 token/min）
- 单 prompt 越长，QPS 越低
- 短 prompt 高并发反而更优

## 三、调优策略

### 3.1 端点并行
- P0 端点 3 并行：保证 codegraph 不拥堵
- P1 端点 5 并行：可降级质量换速度
- P2 端点 10 并行：浅扫

### 3.2 FWD 模式并行
- 4 模式**全并行**（同一端点）：
  - A 数据流（慢）
  - B 鉴权（中）
  - C 业务（中）
  - D 状态（快）
- 共享 Memurai 预取 → 节省 70% 方法体传输

### 3.3 失败重试
```python
for attempt in 1..3:
    try:
        result = subagent.run(...)
        break
    except TimeoutError:
        if attempt == 3: kill_and_log
        else: sleep(2^attempt); continue
    except JSONDecodeError:  # LLM 输出格式错
        re_prompt_with_format_hint()  # 不算 attempt
```

## 四、心跳检测

- 1 小时无回复 → kill
- kill 前先 dump 部分进度到 Memurai（`memurai-cli SET key value`）
- 标记 `subagent_killed_at={time}, completed_chains=[...]`

## 五、性能基准

| 项目规模 | 端点数 | 单轮 Loop 时间 | 期望 |
|----------|--------|---------------|------|
| 小型 | < 50 | < 30 min | 1 轮 |
| 中型 | 50-200 | 30-120 min | 1-2 轮 |
| 大型 | 200-1000 | 2-8 h | 3-5 轮 |
| 超大 | > 1000 | > 8 h | 分批扫描 |

## 六、调优回路

```
单轮时间 > 期望上限
  │
  ├→ 检查 codegraph 慢查询 → 加索引 / 优化 SQL
  │
  ├→ 检查 Memurai 命中率 → 调 key 设计
  │
  ├→ 检查 subagent 失败率 → 调 prompt / 限并发
  │
  └→ 检查 PoC 慢 → 用 playwright 替代手工 / 并发
```
