# 经验 03：剪枝误杀案例

> 剪枝是把"明显不是漏洞"的调用链剪掉，但误剪 = 漏报。

## 一、剪枝的两类失败

| 失败 | 后果 | 信号 |
|------|------|------|
| **漏剪**（剪得不够） | 大量无意义链浪费 token | chain-stats 显示 70%+ 链命中剪枝后才停 |
| **误剪**（剪得过多） | 漏报真实漏洞 | 人工发现某真实漏洞的链被剪掉 |

**误剪比漏剪严重 10 倍**。漏剪 = 慢；误剪 = 漏报。

## 二、剪枝规则评分门槛

- 普通 finding 评分门槛 85
- **剪枝规则门槛 90**（比 finding 更严）
- 单条规则**误杀率** > 5% 即停用（不是 10%）

## 三、误杀率统计

每轮 Loop 结束统计：
```
误杀率 = 已剪掉但实际是漏洞的链数 / 总剪枝数
```

抽样方式：
- 人工抽样 30 条被剪枝的链
- 检查是否有真实漏洞被误剪
- 误杀 ≥ 2 条 → 立即停用规则

## 四、典型误杀场景

### 4.1 框架内部调用误剪
```java
// 看似"内部调用"，实际是用户可控的反射入口
Method.invoke(userInput, ...)  // 危险
```
- 错误剪枝：把 `Method.invoke` 当作 JDK 内部
- 正确做法：检查参数来源是否用户可控

### 4.2 Getter/Setter 误剪
```java
// 看似无害，但 Getter 返回了敏感字段
user.getPasswordHash()  // 拼接到 SQL → 注入
```
- 错误剪枝：剪掉所有 Getter 调用
- 正确做法：只剪"返回基本类型"的 Getter

### 4.3 日志输出误剪
```java
log.info("User input: " + userInput);  // 看似无 sink
```
- 错误剪枝：把日志方法当作 sink
- 正确做法：日志本身不是 sink，但日志泄露是信息泄露漏洞（FWD-INFO）

### 4.4 常量定义误剪
```java
public static final String SQL = "SELECT * FROM users WHERE id = " + CONST_ID;
```
- 错误剪枝：把 `String` 字段当硬编码
- 正确做法：`final` 但通过 + 拼接的，仍可能是漏洞

## 五、剪枝规则文档结构

```markdown
# 剪枝规则 v{N}

## 规则 1：框架内部调用
- 匹配：JDK 内部类 / Spring 内部 / 已审计项目的方法
- 动作：跳过该节点
- 命中率：X% / 误杀率：Y%
- 状态：active / disabled / under-review

## 规则 2：Getter/Setter
- 匹配：方法名 `getXxx`/`setXxx` + 参数/返回为基本类型
- 动作：跳过
- 命中率：X% / 误杀率：Y%
- 状态：active
```

存到 `loop_audit/剪枝规则.md`，每轮更新。

## 六、复审机制

- 命中剪枝的链 → 抽样 30 条人工复核
- 误杀率 > 5% → 立即停用 + 回滚到上一版
- 命中后**仍可被 FWD 主动拉起**（subagent 可读规则后判定"不剪"）
