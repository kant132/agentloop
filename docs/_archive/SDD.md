# SDD: Java 白盒安全审计 Agent Loop

## 1. 战略与目标

### 1.1 三层目标（G1 / G2 / G3）
- **G1 挖掘**：挖掘漏洞并自主验证，不止于发现，要形成可证伪证据（R0.3）
- **G2 资产化**：形成项目安全测试资产——威胁建模、认证鉴权全景、API 资产、4 级漏洞报告、待分析调用链（L10）
- **G3 自优化**：自主发现问题，自主优化迭代 agent loop，把 skill 抽象清楚、沉淀方法论（R0.1 / R0.4）

落地原则：pure_skill 3.0 战略——抽象出战略/原子目标/流程/验收标准（R0.1），AI 在测试中自主造轮子、定义使用方式、定义优化（R0.3），沉淀为漏洞相关 skill 与技巧（污点分析、剪枝、bfs 分析法）（R0.4），轻度融入（R0.5），删除所有无关 skill/文件（R0.6），全文字描述、可拆分多文档（R0.7），明确说明加载的 MCP 服务与 skills（R0.8）。

### 1.2 硬约束（11 条，来自 README § 二）
- L1 第一性原理；L2 执行前先输出规划（原则/标准/需求/原子任务）
- L3-L5 每轮反思打分；L6-L7 调用链打分；L8 心跳 1h kill
- L9 全部 finished + 75% 高危 PoC 通过方可结束
- R0.2 不主动写代码（工具类除外）
- S8 不写修复，业务目标只深度发现致命严重问题
- S9 优先用 codegraph 查询

### 1.3 验收标准（4 个阈值）
- **90**：任一项 < 90 → 优化继续（L4，维度阈值 27/27/27/9/9）
- **85**：连续 3 轮 > 85 → finished（L5 / L7）
- **75%**：高危 PoC 通过率门槛（L9）
- **3x85**：反思打分三项均 > 85 连续 3 轮才结束（L5 + L7 复合）

- PoC 记录过程/结果/根因（P5.9），存 `loop_audit/routes/poc/`（P5.10）
- PoC 文件名 `{验证状态}_{等级}_{fqn.method-sink-round100}`，须与高风险端点文件名一致（P5.11 / P5.12）
- 考虑剪枝逻辑与参数传递分析（P5.13）
- 无法识别风险的 jar/三方服务标"需人工分析"（P5.14）

### 2.6 Phase 6 汇总与自优化（L11 - L13 + 5 项结束条件）

## 3. 工作流（agent 控制，非脚本）

### 3.1 启动检查（I1 - I4）
- `codegraph init` + `codegraph index`（I1）
- Redis 启动（默认端口），缓存 `fqn_method_签名` 到内存（I2）
- 自检保存是否正确，start-1 缺位要补（I3）
- 不会则查 codegraph 文档（I4）

### 3.2 阶段流转决策
- 主 agent 维护状态机：Phase 1 → 2 → 3 → 4 → 5 → 6
- Phase 间 gate：上一阶段产物落盘 + 反思打分过线才推进
- 阶段内自由组合任务，符合奥卡姆——能合并的不拆

### 3.3 心跳 / kill / 失败兜底（L8）
- 心跳 1h 阈值；超时 kill 当前子任务
- 失败兜底：标记 `需人工分析`（P5.14）+ 落盘失败上下文，便于重启接续

### 3.4 自优化循环（L5 / L7 + 三哲学 L13）
- 每轮 30+30+30+10+10 反思打分（L3）→ < 90 优化（L4）
- 每条调用链 30+25+25 评分（L6）→ < 85 补充；连续 3 > 85 finished（L7）
- 三哲学自检：马斯克第一性（剥到本质）/ 康德绝对命令（可普遍化）/ 苏格拉底反诘（质疑前提）

## 4. 关键设计

### 4.1 Redis 批预取（非 read-through）—— I2 详细机制
- 启动期一次性 batch 预取 `fqn_method_签名` 全部进内存
- 运行期不再 read-through；命中内存即返回，未命中则补一次 codegraph 查询并回填
- 子进程开销 ~30ms（memurai-cli 调用），批预取把进程数降到最低

### 4.2 codegraph SQLite 模式（CTE + 20 LEFT JOIN）—— S9
- 优先 codegraph 查询（S9）
- 调用链用 CTE 递归，最大深度 20
- 多跳 join 上限 20，避免爆炸

### 4.3 剪枝 3 层（L1 / L2 / L3）—— P5.13
- L1 类级：白名单/框架类直接剪
- L2 方法级：getter/setter/equals/hashCode 等无副作用剪
- L3 参数级：常量/null/未传播参数剪
- 剪枝规则独立文档，评分 ≥ 90 才归档（O8）

### 4.4 FWD-X 4+1 模式 + 强制重扫
- 4 类漏洞模式（注入/越权/逻辑/信息泄露）+ 1 重扫（sink 点再确认）
- 每类模式跑完强制全量重扫，避免漏报

### 4.5 3x85 评分 + 落盘 —— S10
- Redis 减文件读写：3x85 评分才写文件（S10）
- 评分未达标留在内存继续迭代，落盘前不浪费 IO

### 4.6 数据对账（7+1 项）
- 调用链总数 / 分类统计 / 高危明细（S5）
- API 漏洞数 / 调用链统计 / 业务说明（O6）
- 威胁建模中文 / API 完整 / 漏洞严格分级（O7）
- 过程可信 + 结果可信 + 数据对账一致（S6 / S7）
- 漏报自检（+1）

## 5. 报告输出规范

### 5.1 目录结构（loop_audit/ 12 个子目录）
- `filters/`（P2.6 / S3）、`api_analysis/`（S4）、`routes/{高风险端点,中低险端点}/`（P5.7）
- `routes/poc/`（P5.10）、威胁建模、认证鉴权全景、API 资产、4 级漏洞报告、待分析调用链、剪枝规则、汇总报告

### 5.2 文件命名（O3 + P5.6 + P5.11）
- 端点报告：`{危险等级}_{全限定类名}_{方法名}_{签名Hash}.md`（O3）
- 危险等级取该入口所有调用链最高（O4）
- PoC 文件：`{验证状态}_{问题等级}_{fqn.method-sink-round100}.md`（P5.11）
- PoC 文件名必须与高风险端点文件一致（P5.12）

### 5.3 报告结构 4 段（O5）
- ① 执行摘要
- ② 审计 Checklist
- ③ 细节（含调用链个数 + 致命严重调用链小节）
- ④ 绘图（HTML 调用链 + drawio + Mermaid）（P1.3 / O5④）

### 5.4 绘图（drawio + HTML + Mermaid）—— P1.3 + O5④
- 路由图：drawio（P1.3）
- 调用链：HTML（O5④）支持交互
- 数据流图：Mermaid（P2.2）
- UML：Mermaid classDiagram（P2.4）

## 6. 评分与自检

### 6.1 反思打分（L3）
- 执行 30 + 判断 30 + 思考 30 + 准确 10 + 格式 10 = 100
- 任一项 < 阈值（27/27/27/9/9）→ 优化继续（L4）

### 6.2 调用链打分（L6）
- 污点 30 + 业务 25 + PoC 清晰度 25 = 80 满分
- < 85 补充；连续 3 > 85 finished（L7）

### 6.3 三哲学自检（L13）
- 马斯克：剥到第一性原理（L1 同源）
- 康德：判断可普遍化（评审标准可复用）
- 苏格拉底：反诘前提（质疑假设而非证据）

### 6.4 5 项结束条件
- L9 全部 finished + 75% 高危 PoC 通过
- L5 反思打分 3x85
- L7 调用链打分 3x85
- 75% 资源分配（70/20/10 致命/严重/中危/低危）
- 数据对账一致（S7）
